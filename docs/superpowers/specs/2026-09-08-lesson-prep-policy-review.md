# 수업 준비·세션 문제 선택·과제 조립 — 정책 질문 6건 기획 검토용 정리

> 기획 검토 전용 문서. 코드·마이그레이션·외부 호출 없음. `docs/superpowers/specs/2026-09-08-lesson-prep-session-selection-kickoff.md`(이하 "킥오프 문서") §6의 정책 질문 6건을 아래 형식으로 확장한다. 이 문서는 답을 확정하지 않는다 — 선택지와 권장안만 제시하고, 실제 확정은 기획 검수에서 한다.

## 전제 — 이미 확정된 정책(이번 검토가 반드시 지켜야 하는 경계)

1. 콘텐츠는 **관리자 원본 → 기본 커리큘럼 → 학생별 운영 커리큘럼**의 3단 구조다(2026-09-07 파운데이션 1차 승인).
2. 교사는 **공개(published)·확정(confirmed) 콘텐츠만** 학생별 커리큘럼·수업에 선택한다.
3. **세션 콘텐츠 고정(pin)과 과제 출제 시점** 각각에서 selectable view 기준으로 공개·확정 상태를 다시 검증한다(선택 시점 검사 1회로 끝내지 않음).
4. 수업 중 AI 문제 생성은 없다. AI는 관리자 콘텐츠 초안·해설·키워드 추천 전용.
5. 문제의 "실제 사용"은 **교사의 명시적 사용 처리 또는 학생 답안 제출**로만 기록한다. 단순 열람은 사용이 아니다.
6. 과제는 기존 문제 중 **키워드·문항 수**로 조립하며, 수업 사용 문제·학생 기풀이 문제의 포함 여부는 **교사가 각각 독립적으로 제어**한다.
7. 단어장은 학생 개인 기능. 수업 중 학생이 모르는 단어를 추가하고, **교사가 완료를 확정**한다. 이 흐름은 이번 라운드 범위 밖 — 자동 생성·교사 구성 기능을 추가하지 않는다(2026-09-07 파운데이션 1차 제약 유지).

## 질문 1 — "레슨에서 사용함(used in lesson)" 이벤트의 정확한 단위

**발생 시점**: 실제 수업(세션) 진행 중, 교사가 교재 섹션이나 문제를 학생과 함께 다뤘을 때. 세션뷰의 "교재"/"과제" 탭에서 교사가 특정 항목을 짚고 넘어가는 매 순간.

**선택지별 경험·무결성·운영 부담**

| 선택지 | 교사 경험 | 학생 경험 | 데이터 무결성 | 운영 부담 |
|---|---|---|---|---|
| A. 문제 단위만 기록(교재 섹션은 기록 안 함) | 문제를 풀렸을 때만 버튼, 교재는 그냥 보여줌 — 조작 단순 | 차이 없음(교사 조작이라 학생 화면 무관) | 교재 사용 이력이 전혀 안 남아 "이 수업에서 뭘 가르쳤는지" 복기 불가 | 가장 낮음 — 새 이벤트 하나만 정의 |
| B. 문제+교재 섹션 둘 다, 각각 명시적 버튼 | 교사가 "이 섹션 다뤘음"/"이 문제 풀렸음"을 각각 명시적으로 눌러야 함 — 조작 늘어남 | 차이 없음 | 이력이 가장 풍부(수업 리뷰·품질관리에 활용 가능) | 중간 — 이벤트 타입 2종, UI 버튼 2종 |
| C. 시작/종료 구간 기록(교사가 "이 자료 다루는 중" 토글) | 온/오프 토글 — 실수로 안 끄면 구간이 부정확해짐 | 차이 없음 | 구간 데이터는 분석엔 유리하지만 "안 끔"으로 인한 오염 위험 큼 | 가장 높음 — 상태 관리(시작했는데 종료 안 한 이벤트 처리) 필요 |
| D. 단일 순간 기록(탭 열람은 제외, 명시적 탭/버튼 1회) | 가장 가벼움 — 한 번 누르면 끝 | 차이 없음 | 순간 스냅샷이라 "얼마나 오래 다뤘는지"는 알 수 없지만 "다뤘는지 여부"는 확실 | 가장 낮음 |

**권장안**: **D(단일 순간 기록) + 대상은 문제와 교재 섹션 둘 다(B의 대상 범위 + D의 기록 방식 결합)**. 이유: 이미 확정된 정책 5번("단순 열람은 사용이 아니다")이 "명시적 조작만 기록"을 이미 요구하고 있고, 구간(C)은 "안 끔" 오염 위험이 커서 데이터 무결성을 해칠 수 있다. 순간 기록으로도 "이 수업에서 이 콘텐츠를 실제로 다뤘다"는 사실은 충분히 남고, 나중에 필요하면(성능 문제 없이) 구간 확장은 추가만 하면 되는 additive 변경이다.

**구현 범위 분기점**: 문제 단위만 할지(A) vs 문제+교재(B/D)를 다 할지에 따라 이벤트 테이블이 1종 스키마인지 대상(target_type: material_section | problem) 구분 컬럼이 필요한지가 갈린다. 구간(C)을 택하면 "종료 안 된 진행중 이벤트" 상태 관리 로직이 추가로 필요해 스키마·UI 모두 커진다.

**기존 정책과 충돌**: 없음. 정책 5번과 정확히 부합.

## 질문 2 — 과제 포함 토글 2개의 의미

**발생 시점**: 교사가 수업 후(또는 수업 중) 과제를 조립하는 화면에서, 문제 후보 목록을 좁힐 때.

**선택지**

| 선택지 | 교사 경험 | 학생 경험 | 무결성 | 운영 부담 |
|---|---|---|---|---|
| A. "이번 수업에서 사용한 문제 포함" + "학생이 이미 푼 문제 포함" (질문1의 사용 이벤트 + `session_problem_attempts` 각각을 켜고 끄는 필터) | 수업 복습용 과제(사용한 문제 다시)와 새 문제 위주 과제를 토글 조합으로 쉽게 구성 | 과제에 방금 배운 문제가 다시 나오거나, 완전히 새 문제만 나오거나 선택에 따라 달라짐 — 학생 입장에서 예측 가능한 규칙 | 두 조건 모두 이미 확정 정책(질문5 사용 이벤트, 기존 `session_problem_attempts`)에 근거해 정의가 명확함 | 낮음 — 이미 있는 두 데이터 소스에 대한 필터일 뿐 |
| B. "이번 세션 교재만" vs "전체 단원" (콘텐츠 범위 토글) | 범위를 넓히거나 좁히는 용도 — 하지만 이미 "키워드로 좁힌다"는 조립 방식(정책 6번)과 역할이 겹침 | 차이 없음 | 키워드 필터와 기능이 중복돼 사용자가 둘 중 뭘 써야 할지 헷갈릴 위험 | 낮음이지만 UX 혼란 위험 |
| C. 완전히 다른 의미(예: 난이도, 정답률 등) | 미정 — 계획서에 근거 없음 | 미정 | 계획서에 없는 새 개념 도입 필요 | 새 데이터/집계 필요, 범위 커짐 |

**권장안**: **A**. 이유: 이미 확정된 정책 6번("수업 사용 문제와 학생이 이미 푼 문제의 포함 여부는 교사가 각각 제어")이 사실상 이 두 토글의 정의를 이미 말해주고 있다 — 질문 2는 "정책이 뭐냐"가 아니라 "그 정책을 그대로 두 토글의 라벨/의미로 확정해도 되는가"를 묻는 확인 질문에 가깝다.

**구현 범위 분기점**: A를 택하면 질문1(사용 이벤트)과 기존 `session_problem_attempts`를 그대로 재사용하는 필터 2개만 만들면 되고 새 데이터 소스가 필요 없다. B/C를 택하면 새로운 집계·필터 기준을 설계해야 해서 범위가 커진다.

**기존 정책과 충돌**: 없음(오히려 A는 이미 확정된 문구를 그대로 구현하는 것).

## 질문 3 — "준비된 선택(prepared selection)"의 단위 — 세션당 몇 개까지 고정 가능한가

**발생 시점**: 수업 시작 전, 교사가 다음 수업에서 다룰 단원·키워드를 미리 고를 때.

**선택지**

| 선택지 | 교사 경험 | 학생 경험 | 무결성 | 운영 부담 |
|---|---|---|---|---|
| A. 세션당 오버레이 단원 1개만 고정 | 복습+새 진도를 한 수업에 섞고 싶을 때 불편(두 세션으로 쪼개야 함) | 차이 없음 | 가장 단순 — "세션:단원 = 1:1" | 가장 낮음 |
| B. 세션당 여러 단원/키워드 조합 고정 가능 | 복습+새 단원을 한 수업에 자연스럽게 준비 가능 — 실제 수업 방식과 더 가까움 | 차이 없음 | 여러 단원의 상태 각각(진행중/완료 등)을 어떻게 갱신할지 규칙 필요(예: 세션 완료 시 여러 단원의 진도를 한 번에 갱신) | 중간 — 다대다 관계 테이블 필요, 단원별 진도 갱신 로직 복잡도 증가 |

**권장안**: **B, 단 실제 수업 관행("복습+새 진도")을 반영하는 쪽이 제품 목적에 맞다**. 이유: R8/R9에서 이미 다대다 관계(오버레이 단원↔키워드, 단원↔교재)를 원자적 RPC로 처리하는 패턴이 확립돼 있어(예: `reorder_curriculum_overlay_units`) 기술적으로 새로운 패턴이 아니다. 다만 A가 훨씬 단순하므로, 초기 UAT에서 실제 교사 사용 패턴을 보고 "정말 여러 단원을 한 세션에 고정하는 일이 흔한지" 확인 후 B로 갈지 A로 시작해서 나중에 확장할지는 제품 오너가 결정할 사안.

**구현 범위 분기점**: A는 `sessions.id`에 단일 FK 컬럼만 추가하면 되지만, B는 별도 조인 테이블(`session_prepared_selections`, N:1 sessions→여러 행)이 필요하고 "여러 단원의 진도를 세션 완료 시 어떻게 반영할지" 규칙을 추가로 정의해야 한다.

**기존 정책과 충돌**: 없음. 다만 어느 쪽이든 "세션 콘텐츠 고정"(정책 3번)의 pin 트리거를 단일 컬럼 갱신이 아니라 관계 테이블 삽입/락으로 구현해야 하므로, R8의 `material_version_id` 트리거 패턴을 그대로 재사용하되 "여러 행"에 맞게 확장 필요.

## 질문 4 — 세션 취소·재예약 시 준비된 선택의 이월 여부

**발생 시점**: 교사가 이미 다음 수업을 준비(키워드/단원 고정)했는데, 그 세션이 취소되거나 재예약될 때.

**선택지**

| 선택지 | 교사 경험 | 학생 경험 | 무결성 | 운영 부담 |
|---|---|---|---|---|
| A. 이월(재예약된 새 세션에 그대로 승계) | 취소·재예약이 잦은 상황(체험 취소, 보충 등)에서 다시 준비할 필요 없음 — 편함 | 차이 없음 | "세션:준비=1:1"이 깨짐(취소된 세션과 새 세션이 같은 준비를 공유) — pin 불변식이 어느 세션에 귀속되는지 애매해짐 | 낮음(교사 입장) but 구현은 "취소→재예약" 연결 관계를 명확히 추적해야 함 |
| B. 이월 안 함(취소되면 준비도 폐기, 교사가 재준비) | 매번 다시 골라야 해서 번거로움 | 차이 없음 | 가장 단순 — 세션 하나당 준비 하나, pin은 그 세션에만 귀속 | 가장 낮음(구현 입장) |
| C. "준비 임시보관함"에 남겨두고 교사가 새 세션에 수동으로 다시 붙임 | A(자동)와 B(전부 폐기)의 중간 — 편의성과 단순함의 절충 | 차이 없음 | 세션-준비 관계는 B처럼 단순(1:1)하되, 데이터 자체는 안 지워짐 | 중간 — "임시보관함" UI/데이터 구조 추가 |

**권장안**: **B로 시작**. 이유: R8이 이미 "세션 시작 전(`final_status = scheduled`)까지는 자유롭게 바꿀 수 있고, 그 이후엔 불변"이라는 원칙을 확립해뒀다 — 취소된 세션은 애초에 `final_status`가 다른 값으로 전이되므로, 그 세션에 귀속된 pin을 그대로 "재예약된 별도의 새 `sessions` row"로 이전하는 것은 R8이 지켜온 "세션 하나 = 콘텐츠 스냅샷 하나" 불변식을 흐리게 만든다. 다시 고르는 수고가 있지만(교사 클릭 몇 번), 무결성이 훨씬 단순하고 R9 follow-on의 첫 구현 범위도 작아진다. 실제 UAT에서 재준비가 반복적으로 번거롭다는 피드백이 쌓이면 그때 C(임시보관함) 확장을 검토.

**구현 범위 분기점**: A를 택하면 "취소→재예약" 세션 간 연결(현재 스키마에 이 연결이 있는지 확인 필요 — 없다면 추가 컬럼/테이블 필요)과 그 연결을 통한 이월 로직이 필요해 범위가 커진다. B는 별도 로직 불필요(그냥 새 세션은 준비가 없는 상태로 시작).

**기존 정책과 충돌**: 없음. B는 오히려 R8의 기존 불변식과 가장 잘 맞는다.

## 질문 5 — "레슨에서 사용함" 기록이 학생에게 노출되는지

**발생 시점**: 학생이 자신의 지난 수업/과제 화면을 볼 때, "이 수업에서 다룬 내용"이 표시되는지 여부.

**선택지**

| 선택지 | 교사 경험 | 학생 경험 | 무결성 | 운영 부담 |
|---|---|---|---|---|
| A. 교사 전용(학생 비노출) | 부담 없이 자유롭게 기록(학생이 볼 걸 신경 안 써도 됨) | "오늘 뭘 배웠는지" 복습 화면이 없음 | RLS는 기존 "교사/관리자만" 패턴 그대로 — 가장 단순 | 낮음 |
| B. 학생에게도 노출(예: "오늘 배운 내용" 요약) | 기록이 학생 화면에 그대로 보인다는 걸 의식해야 함(예: 실수로 잘못 누르면 학생이 오해) | 복습에 실질적 도움 — 제품 가치 측면에서 의미 있음 | RLS를 "본인 세션 참여자는 읽기"로 확장해야 함(기존 `session_annotation_events`의 참여자-읽기 패턴 재사용 가능) | 중간 — UI 추가 필요(학생 포털에 "오늘 배운 내용" 섹션) |

**권장안**: **A로 시작, B는 후속 확장으로 남김**. 이유: 이번 follow-on plan의 핵심 목적은 "수업 준비·세션 문제 선택·과제 조립"이지 학생 대상 복습 UI 신설이 아니다(계획서 범위 밖). A로 가면 교사 기록의 RLS는 이미 확립된 "참여자 중 교사/관리자만 쓰기, 필요시 참여자 읽기"에서 "참여자 읽기"를 학생에게 안 열어주는 가장 좁은 버전이라 구현이 단순하고, 나중에 학생 노출이 필요해지면 RLS 정책 추가(additive)로 확장 가능하다.

**구현 범위 분기점**: A는 RLS를 교사/관리자로만 좁히면 끝. B는 그 RLS 확장 + 학생 포털에 새 UI 섹션이 추가로 필요해 범위가 커진다.

**기존 정책과 충돌**: 없음.

## 질문 6 — 키워드 필터링된 eligible-library 쿼리의 성능/인덱스 필요성

**발생 시점**: 실제 콘텐츠 볼륨이 커진 뒤(다수 과목·다수 키워드·다수 문제), 교사가 세션 준비/과제 조립 화면을 열 때마다.

이 질문은 정책 질문이 아니라 이미 킥오프 문서(§4)와 계획서 자체가 "지금 선제적으로 만들지 않는다"고 명시한 **기술 검증 항목**이다. 기획 확정 대상에서 제외하고, 실제 구현 착수 시 개발자가 실측 데이터 볼륨으로 확인 후 필요하면 인덱스/구체화 뷰를 추가하는 것으로 유지 권장(추가 정책 결정 불필요).
