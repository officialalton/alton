# 기획·검수 운영 기준 (2026-09-07)

이 문서는 ALTON의 개발 보고를 기획자가 검수하고 다음 작업을 지시할 때 쓰는
짧은 운영 기준이다. 제품 정책이나 구현 현황을 중복해 적는 문서가 아니다.
현재 상태는 `docs/CURRENT.md`, 전체 실행 순서는
`docs/2026-09-07-planner-status-summary.md`를 우선한다.

## 1. 기획자의 역할

- 사용자 흐름과 정책의 기준선을 정하고, 개발 보고를 코드·migration·테스트·문서와
  필요한 범위에서만 대조한다.
- 기술 선택을 대신 결정하지 않는다. 사용자 경험, 정책, 비용, 외부 실제 쓰기,
  Production, 복구 불가능한 데이터 변경만 제품 오너 결정으로 올린다.
- 발견된 문제는 기존 작업을 다시 만들게 하지 않고, 실제 blocker와 재현 근거만
  하나의 통합 지시로 전달한다.
- UAT에서 새 정책이 확정되면 이전 지시와의 충돌을 즉시 표시하고, 최신 정책을
  단일 기준선으로 갱신한다.

## 2. 작업 착수 전 기준

각 라운드는 하나의 사용자 흐름 또는 하나의 데이터 경계여야 한다. 착수 전에
기획자는 다음 네 항목을 확인한다.

1. **정책**: 대상 사용자, 시작·완료 조건, 제외 범위, 외부 실제 쓰기 여부.
2. **상태와 권한**: 상태 원본, 역할별 권한, 고유 제약, 재시도와 부분 실패 경계.
3. **UAT와 UI**: 정상·빈·오류·취소·재시도 흐름, 모바일·키보드 접근성, Preview에서
   확인할 역할과 계정.
4. **완료 증거**: DB 통합 테스트, 역할별 E2E, 필요한 환경/외부 상태 확인, 문서
   갱신 위치.

정책이 바뀌면 기존 항목을 조용히 병행하지 않는다. 대체된 지시를 문서에 남기고,
개발자는 최신 기준만 구현한다.

## 3. UAT와 데이터 운영

- UAT 데이터는 실행 ID를 기준으로 식별하고, 자동 테스트 데이터·사람이 쓰는
  테스트 계정·공식 계정을 분리한다.
- UAT 시작 전에는 대상 계정과 기존 상태를 확인하고, 종료 후에는 실행 ID 단위의
  정리 결과와 공식 계정 보존 결과를 기록한다.
- 동일 이메일·부분 생성·취소·재발급은 정상적인 운영 시나리오로 본다. 계정·초대·
  가족·카드가 서로 덮어쓰지 않는지 검수한다.
- Preview UAT는 자동 테스트의 대체가 아니다. 자동 테스트로 상태 전이·권한·멱등성을
  고정하고, Preview에서는 실제 역할별 흐름과 화면 경험을 확인한다.

## 4. UI와 성능 검수

- 각 기능은 구현 중 최소 사용성 기준(정보, 행동, 로딩, 빈 상태, 오류, 모바일,
  키보드)을 충족한다.
- 마일스톤 종료 후에는 별도 UI 폴리싱으로 탭 구조, 용어, 정보 밀도, 공통 컴포넌트,
  역할별 일관성을 함께 정리한다. 기능이 모두 끝날 때까지 UI 문제를 미루지 않는다.
- 성능 개선은 기준선 수치 없이 완료로 판단하지 않는다. 쿼리 수, 순차 대기, 서버
  응답 시간, 클라이언트 추가 요청을 같은 조건에서 비교한다.
- 캐싱은 사용자·자녀·권한·시간대와 데이터 신선도, 무효화, 예약 직전 DB 제약을
  함께 검증할 수 있을 때만 적용한다.

## 5. 완료 판정과 다음 단계 전환

개발 보고의 테스트 숫자만으로 완료를 승인하지 않는다. 기획자는 다음을 확인한다.

- 인수 기준의 정상 흐름뿐 아니라 권한 거부, 중복 요청, 동시 요청, 부분 실패와
  재시도에 실제 근거가 있는가.
- migration과 DB 제약이 앱 코드의 가정을 독립적으로 지키는가.
- 중복 화면·서버 액션·레거시 경로가 새 정책을 우회하지 않는가.
- 외부 실제 쓰기와 Production 변경이 승인된 범위 안에 있는가.
- `CURRENT.md`와 기획자 현황 문서가 대상 커밋·검증 결과·남은 범위를 정확히
  반영하는가.

판정은 다음 셋 중 하나만 사용한다.

1. **승인**: 인수 기준과 검증이 모두 충족됐다.
2. **조건부 승인**: 제품 오너 Preview UAT만 남았고 코드·DB·문서 blocker는 없다.
3. **보완 필요**: 실제 blocker와 재현 근거가 있으며, 그 수정이 끝나야 다음 단계로
   넘어갈 수 있다.

다음 마일스톤은 현재 라운드의 정책·상태·검증 기준선이 고정된 뒤에만 시작한다.
단, 서로 파일·테이블·외부 경계가 독립적인 작업은 그 근거를 기록하고 병렬로
진행할 수 있다.

## 6. 보고 형식

개발 보고는 완료, 검증, 미완료, 결정 필요, 외부 변경의 다섯 항목으로 작성한다.
기획자는 이를 바탕으로 하나의 통합 지시만 전달한다. 진행 중간에는 blocker가
있을 때만 보고하며, 완료되지 않은 계획·추정·실행하지 않은 외부 확인을 완료로
기록하지 않는다.
