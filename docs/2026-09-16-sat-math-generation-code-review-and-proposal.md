# SAT Math 생성 개선 — 코드 검토와 제안

작성: 2026-09-16, 기획 검토. 검토 기준 로컬 HEAD `7125a59`.

코드·문서 정적 검토만 수행했다. 테스트, 실제 모델 호출, DB 변경, 배포는 하지 않았다. 아래는 발견 사항과 제안이며 구현 완료 보고가 아니다. R&W 생성 및 진행 중인 단어장 작업은 이번 변경 제안의 대상이 아니다.

## 1. 판단

문제 제작과 답안·해설 작성을 분리한다는 방향은 유지한다. 그러나 현재 문제는 모델의 계산 능력만이 아니다. 검사한 문항과 반환·저장되는 문항이 달라질 수 있고, 검사 오류가 통과로 이어지는 경로도 있다. 이 경로를 먼저 고치지 않으면 생성 모델·프롬프트를 개선해도 결과를 신뢰하기 어렵다.

Math 전체를 즉시 해결하는 범용 계산 엔진보다, 검증 가능한 문제군별 생성기와 해석기를 순서대로 만든다. 기존 표준 렌더러는 그대로 활용하고, 그 앞에 수학적 조건·질문 대상·정답 계산을 담당하는 계층을 추가한다.

관리자에게는 모든 필수 검증을 통과한 완성 후보만 보낸다. 관리자 기본 행동은 공개 또는 보관이다. 시스템 실패 후보를 관리자 수정 업무로 넘기지 않는다.

## 2. 코드에서 확인한 문제

### A. 재생성 결과와 반환 문항이 분리됨 — 최우선

`lib/problem-generation/pipeline.ts:174–191`에서 `fail()`은 재생성한 새 객체를 `gate()`에 넘기지만, 반환하는 것은 `quality`가 든 판정뿐이다. `GateOutcome`에는 검증된 문제 객체가 없다. 이후 `record(g, outcome)`(`:377` 부근)은 최초 객체 `g`를 저장 후보로 채택한다.

따라서 원본 A 실패 → 재생성본 B 통과 → A에 B의 품질 판정이 붙는 경로가 가능하다. 실제 저장은 `app/admin/problem-bank-actions.ts:735`에서 그 객체를 사용한다. 저장 단계에서 별도 검사가 일부 오류를 잡을 수 있지만, 검사 대상과 저장 대상이 달라지는 결함 자체는 남는다.

수정 방향: 성공 결과를 `{ finalProblem, validation }` 한 묶음으로 반환한다. 재생성·부분 수정 후의 최종 내용만 반환하고, 최종 내용 해시에 검증 기록을 연결한다. 저장 직전 내용이 달라지면 검증은 무효다.

### B. 필수 검사가 실행되지 않아도 accepted 가능

`pipeline.ts:270–286`은 독립 검사 예외를 로그로만 남긴다. `review === null`이면 `needsReview`에 사유를 추가한 뒤 `:372`에서 accepted로 반환할 수 있다. 첫 풀이가 불일치했어도 두 번째가 일치하면 낮은 확신으로 통과시킨다.

이는 "관리자는 콘텐츠 채택만 판단"이라는 정책과 맞지 않는다. 검증 상태를 `passed / failed / inconclusive / not_applicable`로 구분하고, 필수 검사의 미실행·불확실을 통과로 해석하지 않는다. 타임아웃은 콘텐츠 오류와 분리해 제한적으로 재시도한다.

### C. 해설에 맞춰 정답을 바꾸는 로직이 두 경로에 남아 있음

`pipeline.ts:242–263`과 `app/admin/problem-bank-actions.ts:399–415` 모두 해설 판정 결과로 정답 인덱스를 변경한다. 저장 시 추가 AI 호출도 발생한다. 저장 뒤에는 파이프라인에서 받은 기존 quality를 붙이므로, 수정된 정답과 이전 검사 기록이 어긋날 수 있다.

수정 방향: 계산으로 확정된 정답은 불변으로 둔다. 해설이 어긋나면 해설을 수리하고 재검증한다. 저장 단계는 검증된 객체를 보존하는 역할만 담당한다. AI 생성 결과와 품질 기록의 저장은 함께 성공하거나 함께 실패해야 한다.

### D. 독립 풀이의 입력이 완전히 독립적이지 않음

`lib/problem-generation/review.ts:129–134`에서 생성기의 `answer_uses_relations`와 선택지 자리별 `distractor_design`을 독립 검사 프롬프트에 넣는다. 정답 인덱스를 직접 주지 않아도 정답 근거와 오답 위치를 유추할 수 있다.

반대로 그림 선택지·복수 자료는 `lib/problem-figures/alt.ts`가 처리하지 않아 `figureAlt()`가 undefined를 반환한다. 독립 검사는 원본 그림 데이터나 실제 이미지를 받지 않고 이 alt만 받으므로, 필요한 자료 없이 판단할 수 있다.

수정 방향: 블라인드 풀이는 학생이 받는 조건·질문·선택지·자료만 받는다. 정답·오답 계획·숨겨진 파생값은 제외한다. 그림 선택지는 각 선택지의 수학적 표현을 빠짐없이 전달하며, 실제 화면 품질 검증은 별도로 수행한다. 독립 풀이 후 설계 의도와 대조하는 것은 가능하다.

### E. 수학 정답 검사 상당 부분이 문장 패턴에 의존

`lib/problem-figures/templates/coordinate-plane.ts:634–658`은 직선 두 개와 "value of x" 같은 문구가 있으면 교점의 x값을 정답으로 가정한다. 실제 질문 대상이 교점인지 구조적으로 명시되어 있지 않다. 수직선·평행선 등은 이 비교에서 빠진다.

`lib/problem-content-check.ts:92–118`의 조건 대입 검사는 특정 일차식 문구와 숫자 선택지 모양을 인식하지 못하면 빈 오류 목록을 반환한다. 이 빈 목록은 "수학적으로 검증됨"과 구분되지 않는다.

수정 방향: `target`을 명시한다. 교점 x, 교점 y, x+y, 기울기, 조건을 만족하는 선택지, 해의 개수 등을 서로 다른 연산으로 구분한다. 적용되지 않은 검사는 not_applicable이며 정답 검증의 근거가 될 수 없다.

### F. 4단계 실험 경로는 계산 엔진이 아님

`lib/problem-generation/math-staged.ts:99`의 `solveMathStem()`은 모델에게 다시 풀게 한다. 독립 생성 호출이라는 점은 개선이지만 수학적으로 확정한 정답은 아니다.

이 경로에는 `parallel_transversal`에 `TRIANGLE_DESC`를 넣는 스키마 설명 혼선(`:27`), 단계 1의 약한 figure 스키마(`:69`), 동일 avoid 목록으로 병렬 생성한 오답끼리 최종 중복 제거를 하지 않는 문제도 있다. 최종 검사가 끝나도 일반 gate로 들어가 검사·재생성 단계가 더 붙는다. 현재 `pipeline.ts:397`에서 비활성화되어 있다.

단순 재활성화보다 수학 모델을 검증하는 작은 새 경로를 먼저 완성하는 편이 낫다.

### G. 오답 부분 수정 후 전체 검증이 다시 이루어지지 않음

`pipeline.ts:317–331`은 고친 선택지를 반영한 뒤 모델 독립 검사를 실행하지만 전체 품질 계약은 재실행하지 않는다. 렌더링·수식·수학적 동치 중복 등의 검사 결과가 수정 전 내용에 머물 수 있다.

`core.ts:619`의 중복 검사는 문자열 정규화 비교다. `1/2`와 `0.5`처럼 수학적으로 같은 답은 별도 처리해야 한다. 수정 계획이 반환되어도 호출부에서는 주로 텍스트만 사용한다.

수정 방향: 변경 범위만 생성하되, 최종 객체 전체에 값싼 결정적 검사를 다시 실행한다. 오답 오류 경로는 설명 문자열 대신 코드가 계산 가능한 연산으로 표현한다.

### H. 기존 통과율·호출 수를 그대로 성과 기준으로 쓰기 어려움

- `pipeline.ts:329–330`: 재검사 직전 countCall과 runReview 내부 countCall로 한 호출이 두 번 집계된다.
- `:473–476`: modelCalls 값은 최종적으로 통과+대기 수로 나눈 평균으로 덮어쓴다. 출력이 0이면 호출 총수를 그대로 반환한다. 따라서 보고서의 "0/5, 문항당 295회"가 정말 한 문항당 295회인지 이 코드만으로 확정할 수 없다.
- `candidatesEvaluated`는 record 시 증가해 재귀 재생성 시도 전체를 세지 않는다.
- 오답 보정 해소 수는 수정 문자열을 반영할 때 증가하며 후속 품질 통과와 동일하지 않다.
- `scripts/problem-quality-batch.ts:107`의 최종 통과율은 통과 수/요청 수다. 후보 자체의 성공률이 아니라 요청 충족률이다.
- API 저장 단계의 추가 AI 호출은 보고서 전용 파이프라인 배치 통계에 포함되지 않는다.

수정 방향: 실제 모델 호출 지점에서 호출 ID, 요청·후보 ID, 단계, 지연시간, 토큰, 종료 사유, 시도 횟수를 기록한다. 총 호출 수, 후보당 호출 수, 저장 완료 문항당 호출 수, 요청 충족률, 후보 통과율, 재생성 해소율을 분리한다.

## 3. 제안 구조: 문제군별 수학 모델 + 기존 렌더러

### 수학 모델에 필요한 것

- 문제군 ID와 버전: 표시용 SAT 기술 코드보다 구체적인 문제 구조.
- givens: 식, 수치, 단위, 도형 관계, 자료 원본.
- domain/constraints: 실수·정수·양수, 분모 0 제외, 범위, 경계 포함 여부.
- target: 무엇을 구하는지. 값·식·좌표·해의 개수·조건 만족 선택지·연구 주장 판단 등을 구분.
- answer policy: 정확값/근삿값, 반올림 자리, 답안 표현 규칙.
- visibility: 학생에게 주는 조건과 내부 파생값을 구분.
- presentation: 자료 종류와 표시 설정. 수학 조건과 레이아웃 좌표를 분리.

그림용 FigureSpec 자체를 수학 문제 모델로 삼지는 않는다. 예컨대 현재 삼각형은 길이 라벨 문자열과 표준 배치를 가진다. 축척과 무관한 도식은 가능하지만, 길이 관계가 실제로 성립하는지는 별도의 수학 모델에서 검사해야 한다.

### 생성 순서

1. 기술 코드·난이도에 맞는 문제군과 변형을 고른다.
2. 검증 가능한 매개변수로 수학 모델을 만든다. AI가 제한된 스키마로 제안하거나 코드가 샘플링한다.
3. 조건 성립·구하는 대상의 결정 가능성을 확인하고 정답 및 풀이 단계 기록을 계산한다.
4. 학생용 문제 문장과 자료를 만든다. 수학 수치·조건은 모델에서 채우고, AI는 맥락과 문장을 담당한다. 작성된 문장이 조건을 추가·누락하지 않는지 확인한다.
5. 같은 모델에서 오개념 연산을 적용해 오답을 계산하고 정답/서로 간 동치 중복을 제거한다. 오답 세 개는 코드로 함께 계산하며 각각 모델을 부르지 않는다.
6. 별도 답안·해설 단계가 검증된 풀이 기록을 설명한다. 정답·조건은 변경할 수 없다. 마지막 답뿐 아니라 중간 계산도 기록과 맞아야 한다.
7. 최종 모델·문장·자료·선택지·해설의 연결 및 화면을 검사한다. 모든 필수 항목을 통과한 객체와 검증 기록을 함께 저장한다.

문제 제작과 답안·해설 작성의 분리는 책임 분리다. 각 논리 단계마다 모델 호출을 새로 만들어야 한다는 뜻은 아니다.

### 첫 문제군 예시

선형 연립에서 원하는 해를 내부적으로 (3, 5)로 잡고, 서로 독립적인 식 `2x+y=11`, `x−y=−2`를 구성할 수 있다. 학생에게 묻는 대상은 `x+y`로 저장한다.

계산기는 다시 풀고 두 식에 대입해 (3, 5)를 검증한 뒤 목표값 8을 계산한다. 렌더러는 같은 두 식으로 직선을 그리고, 선택지·해설도 계산 결과를 사용한다. 내부적으로 해를 선택해 문제를 구성하는 것과, 검증 없이 AI 정답을 믿는 것은 다르다. 학생용 그림에는 숨겨진 해 좌표를 정답 표식으로 넣지 않는다.

이 예시는 계산 일관성 설명용이다. 어려운 문항은 단순히 계수만 키우지 말고 매개변수, 함수 관계, 단위 변환, 해의 개수 판단 등 학습 목표에 맞는 변형을 별도로 설계한다.

### 검증 가능한 범위와 남는 의미 판단

선형 연립·함숫값·비율·도형 공식처럼 명확히 지원하는 연산부터 정확한 분수 계산과 대입 검증을 제공한다. 모든 자유로운 수학 문장을 즉시 풀겠다는 범용 엔진은 만들지 않는다.

연구 설계·통계적 주장·모델 해석처럼 숫자 계산만으로 해결되지 않는 문항은 구조화된 연구 조건과 판단 규칙, 의미 검토를 함께 사용한다. 지원되지 않은 문제군은 미지원으로 기록하고, 같은 코드의 수학 검증 통과로 포장하지 않는다. 이는 최종 시험 범위를 줄이는 결정이 아니라 구현 순서를 명확히 하는 것이다.

정답 유일성은 질문의 답이 결정된다는 뜻이다. 해가 없음/무수히 많음을 묻는 정상 문항은 허용한다. SPR은 서로 다른 표기지만 동치인 답을 같은 값으로 다룬다.

## 4. 속도와 복잡도

검증된 문제군에서는 최초 모델 호출이 문제의 설계·표현을 맡고, 별도 호출이 해설을 맡는 1~2회 중심 구조를 목표로 한다. 실제 시간은 측정 전 보장하지 않는다. 필요한 의미 검토 호출은 별도다.

- 문제군별 작은 스키마만 전달한다. 현재 core는 figure 설명에 대부분의 템플릿을 한꺼번에 넣는다.
- 정답·오답 계산, 스키마 검사, 그림 조판은 코드가 실행한다.
- 라벨 충돌은 레이아웃 후보·여백 조정으로 해결한다. 수학 내용을 새로 생성할 이유가 아니다.
- 수학 사실이 바뀌면 그에 의존하는 정답·자료·해설 검증을 무효화한다. 문구 수정과 수학 조건 수정의 권한을 분리한다.
- 후보별 제한과 요청 전체의 호출·시간·토큰 상한을 함께 둔다. 중첩 재시도가 상한을 곱해서 늘리지 않도록 한 예산을 공유한다.
- 독립된 후보만 제한적으로 병렬 처리한다. 앞 단계 결과가 필요한 작업을 억지로 병렬화하지 않는다.
- 독립 검토 생략은 난이도만으로 결정하지 않는다. 해당 문제군의 수학·문장 연결을 검증할 수 있는 범위를 기준으로 한다.

## 5. 권장 작업 순서와 검증

1. **통과·저장 경로 정상화**: A/B/C/G 및 검증 기록-내용 결합. 이 작업은 AI 표본 대량 생성 없이 재현 가능한 테스트로 확인한다.
2. **단일 문제군 완성**: 두 직선 연립의 교점 및 target 계산. 기존 renderer에 연결해 AI 없는 매개변수 표본부터 검증한다.
3. **실제 생성 연결**: 문제 문장 작성과 해설을 별도 연결한다. 최초 생성부터 DB에 저장된 내용, 관리자 미리보기, 학생 화면까지 동일한 문항인지 확인한다.
4. **확장**: 선형 조건·부등식 → 표/확률/비율/단위 → 함수 → 기하. 우선순위는 실제 실패 빈도와 구현 재사용성을 함께 본다.

필수 검증 사례:

- 원본 실패·재생성본 통과 시 재생성본만 저장됨.
- 필수 검사 예외/미실행/불확실은 공개 후보가 되지 않음.
- 해설이 틀려도 계산 정답은 바뀌지 않음.
- 선택지 변경 후 동치 중복·정답 유일성·수식 검증이 재실행됨.
- 수직/수평/평행/일치 직선, 음수·분수, x/y/x+y, 정의역·단위·근삿값.
- 같은 식을 다른 순서·동치 배수로 표시해도 정답 유지. 단위 변환 후 값의 관계 유지.
- 정답, 부등호, 표 값, 질문 target, 그림 계수 중 하나를 일부러 틀리면 검사가 잡음.
- 블라인드 검사에 생성기의 정답 근거·오답 자리 정보가 전달되지 않음.
- 생성 표본 통과 여부와 별도로 화면에서 선/축/라벨/음영이 올바르게 보임.

운영 지표는 요청 충족률, 후보 통과율, 실제 저장 완료 수, 최초·전체 대기시간, 저장 완료 문항당 모델 비용, 오류 유출 표본을 함께 본다. 통과율만 올리거나 문제군당 10문항 통과만으로 전체 정확성을 선언하지 않는다.
