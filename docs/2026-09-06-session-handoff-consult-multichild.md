## 아직 구현되지 않은 것 (제품 오너가 이번 세션에서 요청한 것 중 남은 부분)

제품 오너의 **최신 확정안(2026-09-06, 이전의 "두 보드 분리" 지시를 대체)**은 다음과 같다.

- 관리자 UI는 **기존 단일 칸반 하나를 유지**한다. 별도 `상담 운영`/`체험·정규 전환 운영` 보드를 만들지 않는다.
- 상담 신청부터 결과 확정 전까지는 보호자/가족 기준의 **상담 건 카드 1개**만 존재한다. 이 시점에는 학생 Auth 계정이나 자녀별 진행 카드를 만들지 않는다.
- 관리자가 상담 결과를 `체험 진행`으로 확정할 때 체험 대상 자녀를 정한다. UI는 `복수 자녀 여부` boolean이 아니라 기본 자녀 1행 + `자녀 추가` 반복 입력으로 1~N명을 받는다.
- 신규 보호자는 보호자 계정/household를 한 번만 만들고, 기존 보호자는 기존 계정/household를 재사용한다. 확정된 체험 대상 자녀는 모두 같은 household에 연결한다.
- 체험 대상 자녀별 온보딩 단위와 칸반 카드는 이 시점에 각각 생성한다. 학생이 초대를 아직 수락하지 않았어도 `학생 정보 준비/초대 대기`를 운영해야 하므로 자녀 카드는 온보딩 생성 시점부터 존재하고, 실제 Auth/student ID는 가입 후 연결할 수 있어야 한다.
- 원 상담 카드는 상담 완료 이력으로 보존하고, 이후 활성 칸반에는 자녀별 카드가 체험 준비→체험→리뷰→정규 전환 단계를 독립적으로 이동한다. 체험 미진행/종료 자녀는 불필요한 활성 카드를 만들지 않는다.
- 상담 공통 일정·Calendar/Meet·상담 동의·상담 Smart Notes·관리자 상담 요약은 원 상담 건에 한 번만 둔다. 학생 초대·체험 동의·체험수업권·배정·예약·리뷰·정규 전환만 자녀별로 관리한다.
- 자녀 카드는 가족ID/householdID와 원 상담건ID로 연결하고 가족 배지·필터로 형제자매를 함께 찾을 수 있게 한다. 동일 상담·동일 자녀 온보딩의 중복 카드/초대/수업권 생성을 DB 제약과 멱등성으로 막는다.
- 단일 칸반에서 상담 구간과 자녀별 진행 구간은 구분선 또는 섹션 라벨만 둔다. 보드 자체를 둘로 나누지 않는다.

**이번 세션에서 위 최신 카드 분기 구조는 구현하지 못했다.** 현재 구현은 상담 1건이 자녀 1명 및 하나의 온보딩만 전제한다. 다만 최신 정책상 상담 신청 단계에서 미리 복수 학생 계정/진행 카드를 만들 필요는 없으며, 핵심 설계 지점은 **체험 진행 확정 시 1~N명의 자녀 온보딩을 만들고 기존 단일 칸반에 자녀별 카드를 생성하는 것**이다.

### 상담과 재원생 면담의 UI 경계(최신 확정)

- 랜딩의 상담은 신규 보호자의 가입 상담이다. 기존 보호자는 보호자 포털의 `자녀 추가 상담`에서 새 자녀 온보딩 상담을 신청한다.
- 보호자 포털의 현재 `가족` 탭에 있는 상담 없는 직접 학생 초대는 기본 흐름에서 제거하고 `새 자녀 상담 신청`으로 연결한다. 기존 초대 로직은 상담 후 확정된 자녀 온보딩에서 재사용한다.
- 랜딩과 보호자 포털의 자녀 추가 상담은 학생 수업 예약과 같은 월간 캘린더→날짜→시간 선택 UI를 공통 컴포넌트로 사용한다. 제출 권한/연결만 비로그인 prospect와 인증 guardian으로 분리한다.
- 기존 자녀의 학습·일정·선생님·서비스 현황 논의는 가입용 `상담`과 섞지 않는다. R11 보호자–관리자 메신저에서 비동기 `문의`를 처리하고, 실시간 대화가 필요할 때 `면담 일정 요청`으로 전환한다. 관리자는 향후 별도 `면담 운영`에서 관리한다.
- 면담도 같은 캘린더 UI를 재사용하되 데이터·상태·운영 화면은 가입 상담과 분리한다. 면담 시간, 별도 가용시간, Smart Notes/동의 정책은 R11 착수 시 확정하며 이번 라운드에는 가짜 면담 UI를 만들지 않는다.

### 다음 세션이 먼저 해야 할 일 (제품 오너 지시 순서 그대로)

제품 오너의 마지막 지시("앞서 보낸 두 지시는 하나의 통합 작업 라운드로 처리")는 **먼저 3분류(이미구현/부분구현/신규구현 필요)를 내부적으로 분류한 뒤 진행**하라고 명시했다. 이번 세션은 이 분류를 문서화된 형태로 보고하지 못한 채 시간이 부족해 인수인계로 전환했다. 다음 세션 시작 시:

1. 이 문서 + 제품 오너의 원문 세 메시지(세션 로그 또는 이전 요약 참고)를 함께 읽고, 아래 표를 최신화한다.
2. **체험 진행 확정 시 1~N 자녀 온보딩 생성**을 핵심 경계로 삼아 실제 마이그레이션 범위를 정한다. 상담 신청 단계에서 학생 계정이나 자녀 진행 카드를 미리 만들지 않는다.
3. 자녀 온보딩은 학생 Auth 가입 전에도 존재할 수 있어야 하며, 가족/원 상담 연결·자녀별 초대 상태·실패 격리·중복 방지를 책임진다. 칸반 stage는 기존 `trial_sessions`/entitlement/배정/예약/리뷰/계약 상태에서 가능한 한 파생하고 동일 상태를 여러 곳에 중복 저장하지 않는다.
4. 위 경계를 만든 뒤 복수 자녀 반복 입력, 자녀별 초대 발송, 체험 동의, entitlement, 리뷰 독립성 및 Smart Notes 비게이트 검증을 연결한다.

### 아직 손대지 못한 나머지 항목(원 지시 ①의 12항목 기준, 우선순위 참고용)

- 체험 진행 확정 단계의 복수 자녀 온보딩 폼(기본 1행 + 자녀 추가, 자녀별 이름/학년/과목/학생 이메일).
- 보호자 포털 `자녀 추가 상담` 및 진행 중/지난 상담 UI, 현재 가족 탭의 직접 초대 진입점 교체.

- 자녀별 독립 초대 발송(현재는 온보딩 링크가 상담 1건당 사실상 1개 자녀만 가정).
- 상담-레벨(회의 참석 전체) vs 체험-레벨(자녀별) Smart Notes 동의 분리 저장 — 현재는 계약 조항 기반 단일 동의 모델(위 6번 항목)이라 이 세분화가 아직 없음. **단, "Smart Notes가 어디서도 게이트가 아니어야 한다"는 요구 자체는 상담 결과 기록 경로에서는 충족됨(위 6번).** 체험 진행/정규 전환 등 다른 경로에 남은 게이트가 있는지 `grep -rn "smart_notes" app/ supabase/migrations/` 로 전수 재확인 필요 — 이번 세션에서 못함.
- 자녀별 entitlement 완전 독립(1건 실패가 형제 자매에 영향 주면 안 됨) — 기존 R4 entitlement 모델이 이미 자녀(child_id) 단위이므로 구조적으로는 이미 독립적일 가능성이 높으나, 명시적으로 검증하는 테스트는 없다.
- 즉시 리뷰 작성 + 나중 도착하는 AI 요약(`lesson_reviews.ai_summary`)이 사람이 작성한 리뷰를 덮어쓰지 않는지 — 컬럼은 이미 있고 게시된 리뷰를 자동 갱신하는 코드 경로 자체가 없으므로 구조적으로는 이미 안전하지만, 이것도 명시적 테스트는 없다.
- 비prod 데이터 정리 — 제품 오너가 `official@alton.education`과 `teacher1@alton.education` 및 필수 운영 데이터만 보존하고 나머지 UAT 고객 데이터를 정리하도록 **명시 승인 완료**. ID allowlist 사전 확인, dry-run, immutable 감사이력 비우회, schema/migration/env/webhook 보존 조건으로 진행한다. 재확인 질문은 불필요하다.
