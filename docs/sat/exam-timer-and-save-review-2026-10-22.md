## 1. 답안 0행 vs 클라이언트 저장 실패 가능성 (구분)
- **서버 사실**: `mock_exam_answers`에 이 응시의 행이 0개. 이것은 "서버에 저장된 답이 없다"는 사실이다. 학생이 답을 선택했는지 여부는 알려 주지 않는다.
- **저장 실패 가능성**(클라이언트 경로 점검 결과, 코드 근거):
  1. `MockExamMstTakeClient.saveAnswer`는 선택을 **먼저 화면에 반영(낙관 갱신)** 한 뒤 서버 액션을 호출한다. 객관식 선택은 `void saveAnswer(...)`로 호출하고 `saveAnswer`에 try/catch가 없다. 서버 액션 호출 자체가 네트워크 오류로 reject되면 **오류 표시도 재시도도 없이 조용히 실패**하고 화면에는 선택이 남는다.
  2. 서버가 오류를 돌려주는 경우(`r.ok=false`)는 `setError`로 배너를 띄우지만, 그 배너는 **다음 저장이 성공하면 지워진다**(`setError(null)`). 실패한 문항은 표시되지 않고 재시도도 없다.
  3. 낙관 갱신된 선택은 저장 실패 시 되돌리지 않는다(`toggleSaved/Guessed`는 되돌리지만 `saveAnswer`는 아님).
  4. SPR(주관식) 입력은 400ms 디바운스인데 모듈 제출(자동 제출 포함) 직전에 대기 중인 저장을 비우지 않는다. 만료 직전 마지막 입력은 잠금 뒤 "already been submitted"로 거부될 수 있다(영향: 마지막 몇 글자, 낮음).
- **서버 기록 충분성**: `lib/mock-exam/attempt-actions.ts`·`mst-actions.ts`에는 `console.*` 로그가 없고 오류는 클라이언트로 문자열만 돌려준다. **저장 실패는 서버 로그에 남지 않는다.** 그래서 과거 응시의 원인은 이 구조로는 복원할 수 없다. 이번 조회 구간 Vercel 오류 로그도 조회되지 않았다(보존 한계 또는 무오류).
- **개인정보**: 답안 내용(선택값)을 로그로 남기는 코드는 없다. 현재는 로그 자체가 없으므로 불필요한 기록 문제는 없다. 개선 시에도 답안 값·이름·메일은 남기지 않는다.
- **원인 판단**: 이 응시의 0행 원인은 **미확인**(학생이 답하지 않음, 저장 실패, 기타 모두 가능). 위 1~3은 "저장 실패가 있어도 학생에게 알려 주지 못할 수 있다"는 설계상 공백이며 이 응시의 원인으로 입증된 것이 아니다.
- **최소 개선 제안(구현하지 않음)**: (a) `saveAnswer` try/catch와 문항별 "저장 안 됨" 표시, 자동 재시도(예: 3회 백오프) 후 실패 유지 배너(다음 성공으로 지우지 않고 해당 문항이 저장돼야 해제); (b) 모듈 제출·자동 제출 직전 대기 중인 SPR 저장 비우기와 미저장 항목이 있으면 경고; (c) 서버 액션에서 실패 시 구조화 로그(attempt id, set item id, 오류 코드, 시각만; 답안 값 제외); (d) 연속 실패 시 클라이언트가 한 번 보고하는 경량 비콘.

## 2. 타이머 설계와 실제 동작
- **설계(코드)**: 서버가 권위. 시작 RPC가 모듈 5개(rw_m1, rw_m2, break, math_m1, math_m2)를 만들고 rw_m1 타이머를 `now()`에서 시작한다. 모듈이 잠기면(`_mock_exam_lock_module`) `_mock_exam_open_next_module`이 **다음 모듈의 타이머를 그 순간 `now()`로 즉시 시작**한다(휴식 포함, 휴식 600초는 자동으로 흐른다). 이것은 코드 주석("다음 모듈 타이머도 이 RPC 시각에 시작")대로 의도된 연속 흐름이다. 따라서 "학생이 아직 시작하지 않은 모듈의 타이머가 시작되는가?"에 대한 답: **예, 설계상 이전 모듈이 잠기는 즉시 다음 모듈 타이머가 시작된다.**
- **만료 처리는 "지연 평가"**: 만료(`ends_at` 경과)는 누군가 RPC를 호출할 때(`_mock_exam_settle`, 상태 조회·답 저장·제출 진입 시) 비로소 처리된다. 서버 타이머·크론으로 만료 응시를 닫는 작업은 없다(`vercel.json`의 크론에 해당 없음). 클라이언트는 1초 틱으로 남은 시간이 0이 되면 `submitMstModuleAction`을 한 번 호출한다(실패해도 같은 모듈에 대해 재호출하지 않음: `autoSubmittedForRef`).
- **불일치 1 — 주석과 동작이 다르다(결함 후보)**: `_mock_exam_settle` 주석은 "오래 이탈한 경우 연쇄 처리"라고 하지만, 다음 모듈 시작을 `now()`로 하므로 루프는 **연쇄 처리를 하지 않는다**(방금 시작한 다음 모듈은 만료 전이라 루프가 즉시 끝난다). 실제 증거: df04cb6b의 math_m1은 23:17:24에 만료됐으나 23:47:08(+29분 44초)에 잠겼고, 바로 그 시각에 math_m2가 **새 35분 타이머로 시작**(23:47:08~00:22:08)했다. 즉 오래 자리를 비운 학생이 돌아오면 이전 모듈만 잠기고 **다음 모듈은 처음 시간으로 다시 시작**된다.
  - 영향: 학생이 모듈 사이에 오래 이탈해도 다음 모듈에서 전체 시간을 다시 받는다(시험 시간 무결성). 연습용 제품이라 점수 위조 문제는 아니지만 "타임드 모의고사" 의미와 통계(시간 초과 응시)에 영향. 잠긴 이전 모듈은 만료 시각과 무관하게 채점되므로 점수 자체는 바뀌지 않는다.
  - 심각도: 중간(시간 무결성·통계 왜곡, 데이터 손실 없음). 별도 결함으로 기록한다(하단).
- **df04cb6b의 연속 자동 제출 해석**: 모듈마다 만료 후 서로 다른 지연으로 잠겼다(+44초, +8초, +2분51초, +29분44초, +28초). 한꺼번에 몰아서 처리된 것이 아니다. 열려 있던 클라이언트의 자동 제출(탭이 백그라운드이면 브라우저가 타이머를 늦춤)이나 학생의 화면 진입이 서로 다른 시점에 RPC를 호출한 것과 일치한다. **누가/무엇이 호출했는지는 확인할 수 없다.** 이 지연 패턴은 "화면이 계속 열려 있었을 가능성"과 "기기 절전·탭 중단"이 모두 가능하며, 어느 쪽인지, 학생이 답을 눌렀는지는 판단할 근거가 없다.
- **설계와 실제 동작 일치 여부**: 서버 권위 타이머·즉시 다음 모듈 시작·클라이언트 자동 제출은 설계대로 동작한다. 불일치는 위 "연쇄 처리" 주석 대 실제 동작 한 가지다.

## 3. 결함 기록 (수정하지 않음)
- **D-TIMER-1 (중간)**: 이탈 후 복귀 시 다음 모듈이 `now()` 기준 전체 시간으로 시작(연쇄 만료 처리 안 됨).

  - 제안: 정책 확정 후 `_mock_exam_open_next_module`의 시작 기준을 이전 `ends_at`로 하는 새 마이그레이션(오너 승인 필요).
- **D-SAVE-1 (중간)**: 답 저장 실패가 조용히 사라질 수 있음(§1 1~3). 재현: 응시 중 네트워크 차단(오프라인) 후 보기 클릭 → 화면에는 선택이 남고 오류 표시·재시도가 없음.
- **D-SAVE-2 (낮음)**: 모듈 제출 직전 대기 중인 SPR 디바운스 저장 미반영(§1-4).
- **관측 한계**: 서버가 저장 실패를 기록하지 않아 과거 사례(df04cb6b 포함)의 원인 복원 불가.
