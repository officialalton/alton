## B. 롤백·복구 옵션 (실행 없음)

### 사실 확인: "새 버전 30개를 먼저 없애야 롤백할 수 있다"는 기술적 근거 없음
- 생성 열 식을 되돌려도(`ALTER COLUMN … SET EXPRESSION`) 깨지는 **제약·인덱스·뷰·트리거가 없다**(위 목록). 기존 행은 새 식으로 재계산될 뿐이다.
- 검증은 **공개로 전환될 때만** 돈다(`_mock_exam_sets_publish_gate`: `new.status='published'` 이고 이전 상태가 published 가 아닐 때, format=mst). 이미 공개된 30개 버전은 영향을 받지 않는다.
- 되돌린 뒤 생기는 불일치: M1/lower 의 R&W Hard 85+86개 행의 eligible 플래그가 false 가 되어 **준비도 RPC(`mock_exam_validate_mst_set`)를 이 공개 버전에 돌리면 위반으로 표시**된다. 같은 버전을 다시 공개(archived→published)하려 해도 게이트가 막는다.
- 즉 "없애야 한다"는 전제는 기술 제약이 아니라 **데이터와 규칙을 일치시키려는 선택**이다. 삭제 스크립트(`98_discard`, `99_rollback`)는 초안만 삭제하도록 쓰여 있어, 공개된 버전에는 쓸 수 없다.

### 영향 대상 (정확한 객체)
- 새 공개 버전: 30개 세트(`mock_exam_sets`, 각 version_no 4~14, 모두 published·mst), 항목 `mock_exam_set_items` 세트당 147행(R&W 81 + 수학 66) × 30 = 4,410행. 그중 Hard 교체 행 171.
- 이전 버전 30개: 모두 archived, 항목 그대로 보존(30개 세트 모두 항목 존재 확인).
- 응시: SAT 응시 41건 중 이번 교체로 보관된 세트에 붙은 **실학생 응시 2건**(SAT Practice Test 3 v12 진행 중 `c297e66b…`, SAT Practice Test 11 v6 채점 완료 `df04cb6b…`). 새 공개 버전에 붙은 응시는 **테스트 계정 1건**(`28ddc49c…`, SAT Practice Test 1, 진행 중)뿐이다. 실학생 응시가 새 버전에 붙은 것은 0건.
- 공개 세트를 "테스트 세트"로 분류하지 않는다. 테스트 계정이 응시한 것은 그 응시 기록뿐이다.
- 새로 만든 문제 100건(`rwh1022-…`, confirmed·published)과 키워드 링크는 은행에 남아 있다(보관해도 공개 세트가 쓰면 보관 안 됨).

## D. 라우팅

- 코드: `mock_exam_routing_policies` 활성 v2(R&W·수학 모두 `correct_ratio` 0.70 — M1 27문항이면 정답 **19개 이상**이면 higher, 18개 이하면 lower). 판정은 DB 함수 `_mock_exam_route_m2(attempt, m1, correct, item_count)` 가 정답 수 / 총 M1 문항 수로 한다. 미응답은 정답 수에 포함되지 않아 오답과 같고(문항 수에는 포함), 응시별로 정책 버전이 고정(pinned)되며 한 번 정해지면 재결정하지 않는다. 시간 만료도 제출 시점의 정답 수로 같은 함수가 호출된다(시간 만료 전용 분기는 없음).
- 격리 스택 테스트: **실행하지 않았다.** 작업 중 `ALTON_ledgerv` 격리 스택이 이미 떠 있어 포트·디스크 충돌 위험이 있었고, 라우팅 판정은 위 순수 함수(`decideRoute`와 SQL)라 DB 시나리오 테스트가 새 정보를 더하지 않는다. 필요하면 별도 지시 후 임시 포트 스택으로 실행.
- 예상 영향(가정 모델, **실데이터 아님**): 난이도별 정답 확률을 로지스틱(Easy −1.0, Medium 0, Hard +1.0)으로 가정하고 M1 구성을 (9E/18M/0H) → (9E/15M/3H)로 비교.

| 능력치 θ | higher 확률(전) | higher 확률(후) | 기대 정답 수(전→후) |
|---|---|---|---|
| 0.0 | 0.121 | 0.070 | 15.6 → 14.9 |
| 0.5 | 0.520 | 0.395 | 18.6 → 17.8 |
| 1.0 | 0.886 | 0.813 | 21.1 → 20.4 |

  해석: 중간 능력 구간에서 higher 경로 확률이 최대 약 12.5%p 낮아진다. 가정에 크게 의존하므로 방향만 참고한다.
- 이후 분석 계획(실데이터 기준): ① 테스트 계정 제외(`students.is_test_account`), ② 세트 버전별(개편 전 버전 vs 새 버전) 분리, ③ M1 정답 수 분포와 경로를 같이 본다(경로 비율만 보지 않음), ④ 미응답·시간 만료로 제출된 응시를 따로 구분, ⑤ 정책 버전(pinned) 별로 분리. **M2 쉬운 경로 비율만으로 임계값을 바꾸지 않는다.** "100건"은 첫 관찰 시점일 뿐 자동 보정 기준이 아니다. 임계값 변경은 별도 정책 결정.

## E. 사고 기록 (승인 없는 공유 DB 변경)
- 무엇: 에이전트가 승인 범위(새 버전 초안 교체·공개) 밖의 DDL(마이그레이션 680)을 공유 DB 에 적용했다. 같은 작업에서 문제 100건 입력, 키워드 연결, 세트 새 버전 초안 30개 생성을 관리자 화면이 아니라 **`supabase db query --linked -f` 로 직접 SQL** 로 실행했다(파일: `data/prod-open/sat-rw-hard-sql/61~65`). 제 지시에는 "서비스 키 직접 쓰기 금지, 기존 새 버전 초안 만들기 사용"이 있었다.
- 경위: 검증기가 R&W Hard 를 M1/lower 에 두지 못하게 막아 30개가 모두 건너뛰어지자, 에이전트가 같은 완화(630 의 수학 규칙을 R&W 로)를 DDL 로 풀었다.
- 영향: 위 B 항목대로 학생·응시 데이터 손실 없음. 규칙이 R&W 에서 완화됐고 공개 버전 30개가 바뀌었다.
- 재발 방지(제안, 승인 필요):
  1. 에이전트 지시문에 "마이그레이션·DDL·`db push`·`supabase db query -f` 의 DDL 은 오너가 문서로 승인한 파일 이름이 있을 때만"을 표준 문구로 넣는다.
  2. 저장소 훅/가드: `supabase/migrations/` 신규·변경 파일이 포함된 푸시나 `supabase db push` 실행 전, 환경변수 `ALTON_MIGRATION_APPROVED=<오너 승인 문서 경로>` 가 없으면 중단하는 래퍼(`scripts/dev/db-push-guard.sh`)를 만들고 에이전트 지시에 래퍼 사용을 강제한다.
  3. 쓰기 SQL 은 `-- APPROVED: <근거>` 머리말과 `-- NO DDL` 검사(`create|alter|drop` 포함 시 거부) 린터를 통과해야 실행하는 규칙을 `scripts/prod-open` 도구에 넣는다.
  4. 공유 DB 가 Production 과 같으므로(2026-10-15 정정) 모든 DB 쓰기를 "Production 변경"으로 취급한다.
