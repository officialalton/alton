# PDF·영상 순차 교재 — 페이지별 필기 구현성 확인

2026-09-14. 코드 조사 + 기존 단위 테스트 실행 + 현재 컴포넌트의 전환/저장 경계 재현.

## 결론과 정책

사용자가 이번 대화에서 현재 정책을 수용했다: PDF·영상 파일을 순서대로 등록하고, PDF는 페이지별로 교사/학생 필기를 저장한다. 영상에는 필기를 추가하지 않는다. 이번 확인에서 정책을 다시 바꾸지 않았다. Google Slides 직접 연동보다 이 흐름을 우선한다.

**구현 가능하며, 필기 전체 재개발은 불필요하다. 다만 ‘페이지 번호만 추가하는 작은 수정’은 아니다.** 신규 PDF 페이지 뷰어, 페이지 단위 저장 대상, 전환/복구 처리, 실시간 범위 보완이 필요한 중간 규모의 기능 변경으로 판단한다. 코드 조사로 확정할 수 있는 것은 변경 경계이며, 실제 PDF·DB·다중 브라우저 통합의 성공이나 일정은 아직 확정할 수 없다.

## 확인한 현행 구조

- `MaterialAnnotationLayers.tsx:82`: 브라우저 임시 저장 키는 계정·수업·교재·레이어. 자료 항목/페이지/배포 버전이 없다.
- 같은 파일 `:235`: Realtime 채널도 수업·교재 단위이며, 메시지는 scope와 seg만 담는다.
- 같은 파일 `:252`: 저장 시 pendingRef를 먼저 비우고 서버 응답을 기다린다. `:277`에서 마지막 펜 입력 종료 후 600ms 지연 저장한다.
- `annotation-events-actions.ts:48`: 저장 RPC 인자에 페이지가 없다. `:131`, `:159`의 조회도 수업·교재·scope로 필터한다.
- `20261304000000_p3_student_shared_material_layer.sql:101`: 기존 append RPC와 작성자/학생 소유자 결정은 재사용 가능. PDF 항목/페이지/버전 검증은 추가해야 한다.
- `annotation-scale.ts`: 기준 너비에 대한 좌표 변환은 재사용 가능. PDF의 고정 비율과 페이지별 크기로 맞추고 렌더가 끝난 뒤 입력을 열어야 한다.
- 현재 package.json에는 PDF.js/react-pdf가 없고, 교재용 PDF 페이지 렌더러도 조사한 경로에서 찾지 못했다. 기존 PDF MIME·문서 다운로드 지원은 교재 페이지 렌더링 지원과 다르다.

## 실제 테스트 결과

기존 3개 파일 29개 테스트 통과:

- `MaterialAnnotationLayers.test.tsx`: 12개 — 역할/토글/저장 호출/임시보관/실패 표시.
- `annotation-scale.test.ts`: 8개 — 크기 변경과 좌표 환산.
- `annotation-events-actions.test.ts`: 9개 — 기존 액션 경로.

조사용 임시 테스트에 기존 12개 + 새 재현 2개를 넣어 14개 통과. **새 2개는 정상 기능 합격 테스트가 아니라 현재 한계가 실제 발생하는지 확인하는 테스트**다. 기존 12개는 중복 실행이므로 고유 검증은 기존 29개 + 재현 2개다. 서버 액션·Realtime·캔버스는 mock한 컴포넌트 테스트이며 실제 저장 DB나 픽셀/영상 검증이 아니다.

### 재현 1 — 대상 전환 시 미저장 필기 혼합

1. doc-A로 컴포넌트를 열고 한 획을 쓴다.
2. 600ms 저장 전에 동일 컴포넌트를 doc-B로 rerender한다.
3. 한 획을 더 쓰고 저장 타이머를 진행한다.
4. **doc-B 저장 호출 한 번에 A와 B의 두 획이 함께 전달됨**을 확인했다.

이는 현재 앱에서 실제 PDF 페이지 간 유출이 발생했다는 뜻은 아니다(PDF 페이지 기능 자체가 없음). 같은 컴포넌트의 대상만 바꿔 페이지 전환을 붙이는 구현은 안전하지 않다는 증거다. 새 화면으로 재마운트하는 것만으로 해결됐다고 간주하지 말고 이전 저장의 완료·실패·재접속도 다뤄야 한다.

### 재현 2 — 서버 응답 전 복구 기록 불완전

1. 첫 획 저장 요청을 보내고 서버 응답을 미완료로 유지한다.
2. 그 사이 두 번째 획을 쓴다.
3. 아직 어느 획도 서버 저장 확인을 받지 않았지만 localStorage에는 두 번째 획만 남는다.

서버 저장이 성공하면 반드시 유실되는 것은 아니다. 하지만 그 상태에서 화면이 닫히고 첫 요청이 커밋되지 않으면 복구할 첫 획이 없다. 서버 확인 전 pending+in-flight 전체를 보존하고, 재시도용 안정된 ID로 중복을 막아야 한다.

조사용 테스트는 현재 오류 동작을 정답으로 고정하지 않도록 앱 테스트 목록에서 제거했다. 재현 절차와 결과는 이 문서에 남겼다.

## 필요한 변경을 최소로 제한하는 설계

| 작업 | 최소 변경 |
| --- | --- |
| PDF 표시 | 성숙한 PDF 라이브러리로 한 페이지씩 렌더. 브라우저 내장 PDF iframe 위에 얹지 않음. 늦게 끝난 이전 페이지 렌더 결과가 현재 페이지를 덮지 않게 처리 |
| 자료 순서 | 교재 배포 버전에 불변 자료 항목 ID, 종류(pdf/video), 순서, 자산 버전, PDF 페이지 수 보존 |
| 필기 대상 | 수업 + 배포 버전 + 자료 항목 + 페이지 + scope. 자료 항목 ID는 업로드 위치/배열 인덱스가 아님 |
| 저장 | 기존 이벤트 테이블/RPC를 확장. 실제 수업의 배포 항목이고 유효 PDF 페이지인지 서버 검증. 과거 Native 필기는 새 필드 NULL로 유지 |
| 전환·복원 | 파일/페이지마다 메모리·임시저장·조회 범위를 분리. 첫 버전은 저장 완료 전 다음/이전 이동을 잠깐 막고 실패 시 재시도 표시. 별도로 닫기/통신 단절용 복구 큐 유지 |
| 실시간 | 페이지 대상과 이벤트 ID를 포함하고 현재 페이지에만 그리기. 재연결 시 서버 기준 보충. DB 권한과 별개로 채널 권한도 검증 |
| 좌표·지우개 | PDF 페이지 기준 좌표 사용. teacher/student를 별도 캔버스 또는 독립 버퍼에 그려 자기 지우개가 상대 필기를 지우지 않게 처리 |

지우개는 코드상 추가 주의점이다. 현재 `MaterialAnnotationLayers.tsx:119`는 두 논리 레이어를 같은 캔버스에 순서대로 그리고, 지우개는 destination-out을 사용한다. 상대 레이어의 픽셀까지 지울 수 있는 구조이므로 그대로 재사용하지 않는다. 이번에는 실제 브라우저 픽셀 테스트로 재현하지 않았으며 코드 검토 결과로 구분한다.

PDF 한 페이지 렌더와 이전/다음 처리는 PDF.js 공식 예제로 지원 경로를 확인했다. 자체 PDF 파서를 만들 필요는 없다. [PDF.js 공식 예제](https://mozilla.github.io/pdf.js/examples/)

## 다음 구현의 완료 조건

정책 변경 없이 2페이지 PDF 하나로 먼저 검증한다. A-1→A-2→A-1, 새로고침, 저장 응답 지연·실패·재시도, 동일 수업 교사/학생 두 브라우저, 상대 레이어 지우개 보존, 비참여자 접근 차단, 기존 Native 과거 조회를 통과시켜야 한다. 이어 PDF A→영상→PDF B 순서 이동과 파일별 필기 분리를 확인한다.

이번 실행은 그 구현에 앞선 확인이다. 실제 PDF fixture 렌더, 새 페이지 스키마 구현, DB/RLS 통합 테스트, 영상 재생, Preview UAT는 **미실행**이다. 앱 코드·의존성·DB·배포·외부 서비스는 변경하지 않았다. 기존 테스트와 재현이 확인한 범위를 넘어 ‘페이지별 필기 구현 완료’로 보고하지 않는다.
