# 포털 로딩 코드 전수 점검 — 2026-09-10

## 범위와 한계

이 문서는 코드 경로와 기존 로컬/Preview UAT 관찰값을 대조한 조사다. Vercel
Deployment Protection 때문에 조사자가 Preview 브라우저의 실제 클릭-렌더 시간을 직접
측정할 수는 없다. 따라서 **시간 수치**는 제품 오너가 관찰한 값 또는 기존 로컬
프로덕션 빌드 측정값만 썼고, **원인**은 소스 코드에 존재하는 호출 구조를 근거로
기록한다. 코드·DB·Preview·Production 변경 없음.

## 결론

긴 로딩은 하나의 느린 DB 쿼리가 아니라 다음 네 가지 구조가 겹친 결과다.

1. 포털 페이지가 현재 탭과 무관한 데이터를 처음부터 전부 읽는다.
2. 목록 화면이 목록에 필요 없는 상세·통계까지 함께 조립한다.
3. 한 화면의 여러 서버 액션이 각자 인증을 다시 하고, 일부 호출이 순차다.
4. 데이터 도착 전 스켈레톤이 없거나 텍스트만 있어, 실제 대기보다 더 긴 빈 화면으로
   체감된다.

한 번 방문한 탭이 빨라지는 현상은 Shell 컴포넌트가 받은 props와 로컬 state를 유지하는
효과다. 이는 첫 진입 4~20초 문제를 해결하지 않는다.

## 관리자

### 사용자 — 가장 명확한 15~20초 후보

`app/admin/page.tsx`는 `tab=users`일 때 학부모·학생·교사 목록을 모두 SSR에서
동시에 읽고, 그 뒤 학생 수업권 이력과 교사 QC 이력도 추가로 읽는다(95~97, 120~123행).
그러나 UI의 최초 선택 탭은 학부모다.

각 목록 로더는 내부에서 순차 네트워크 왕복을 만든다.

| 목록 | 현재 내부 조회 | 목록 첫 화면에 불필요한 데이터 |
| --- | --- | --- |
| 학부모 | 부모 → 가구 보호자 관계 → 자녀 관계 → Auth 이메일 | 다른 역할 전체 목록 |
| 학생 | 학생 → 가구 관계 → 보호자 관계 → 수강 과목 → Auth 이메일 → AP 과목 → 비교과 | AP·비교과·수강 과목·수업권 이력 |
| 교사 | 교사 → 수강 과목 → QC 경고 → 운영 템플릿 → Auth 이메일 | QC 상세·운영 템플릿 |

`loadEmailById()`는 세 로더마다 `auth.admin.listUsers({ perPage: 200 })`를 별도로
호출한다(`users-data.ts` 68~76행). 같은 이메일 목록을 최대 세 번 받는다. 학생 목록은
매칭에도 재사용되어, 매칭 대기 카드에 필요한 이름·학년·보호자보다 훨씬 많은 필드를
가져온다.

**개선 우선순위:** 역할별 경량 목록 로더, 현재 선택 역할만 지연 로드, 이메일 조회
단일화, 상세 패널에서만 AP·비교과·이력·QC 로드, 페이지네이션/limit, 목록 스켈레톤.

### 매칭 — 제품 오너 관찰 약 15초

`MatchingTab`은 `students` 전체를 `status === pending`으로 필터할 뿐이다
(`MatchingTab.tsx` 24~26행). 하지만 `page.tsx`는 그 `students`에 위 학생 상세
`loadStudents()` 전체를 사용한다(96행). 매칭의 실제 최소 데이터는 학생 ID·이름·학년·
보호자·상태다. 과목 카탈로그와 교사 후보도 같은 SSR 응답에서 필요하지만, 학생 상세
조회와 결합될 이유는 없다.

매칭 화면은 추가로 수강 배정 패널·종료 요청 패널·체험 온보딩 패널을 함께 렌더한다.
이들 클라이언트 패널은 각자 mount 후 action을 호출하므로, 최초 목록과 독립된 하위
데이터도 초기 체감에 섞인다.

**개선 우선순위:** 전용 `loadPendingMatchStudents` 경량 로더, 목록/확정 상세 분리,
하위 패널 접기 또는 실제 열 때 지연 로드, 총 회차 수 오류 수정 및 매칭 공통화와
독립적으로 성능 검증.

### 상담/신규 — 제품 오너 관찰 실제 카드 약 4초

P1-3 1차에서 마운트 후 칸반 POST는 제거됐고 SSR 로더도 탭별로 게이팅됐다.
그러나 `tab=consult`는 상담 목록, 체험, 제안, 동의, Drive/계약 예외, 계약 재시도,
칸반을 함께 읽는다(`page.tsx` 98~108행). 칸반 카드 단계 계산과 과거 이력의 분리가
후속 과제다. 스켈레톤은 빈 화면을 줄이지만 첫 실제 카드 4초를 해결하지 않는다.

**개선 우선순위:** 통합 ‘신규’ 보드 설계 시 카드별 최소 요약을 먼저 제공하고,
과거 상담·체험 상세·계약/Drive 예외는 카드/하위 탭을 열 때 읽는다. 지인 추천
온보딩은 가짜 상담 행을 만들지 않고 공통 view model로 합친다.

### 독립 서버 액션 탭

기존 구조 조사에서 다음이 확인됐다.

- 문의·면담: 3개 action이 병렬이나, 각 action이 별도 인증 체인을 수행.
- 예약 운영/Calendar 동기화: 최초 mount에서 8개 action, 각 action이 인증을 반복.
  제품 오너 관찰 약 5초. Calendar 재처리는 별도 버튼의 외부 API 반복 호출이다.
- 통합 일정: self-fetch 1개이나 날짜 범위/limit 없이 읽어 클라이언트에서 거른다.
- 선생님 배정 종료 요청: self-fetch action, 데이터 전에는 null을 렌더해 무표시.
- 지인/추천 발송 내역: 배치 `.in()` 두 쿼리 중심이라 상대적으로 약 1초.

**개선 우선순위:** 화면별 결합 초기 로더(인증 한 번), 날짜 범위/limit, 하위 영역
스켈레톤. `React.cache()`는 동일 서버 요청 안에서만 보조 수단으로 쓰며 여러 브라우저
action 요청을 공유하는 해법으로 사용하지 않는다.

## 학생 포털

`app/student/page.tsx`는 URL의 `tab`을 읽지만 데이터 로딩에는 쓰지 않는다. 첫 응답에서
대시보드·예약·단어장·문제 기록·수업 이력·커리큘럼·레거시/ v3 과제·교재·수업권·통계·
수강·교사 목록 등 13개 작업을 동시에 시작한다(40~68행). 이후 커리큘럼마다 메모를,
교사마다 프로필·이력·채팅 스레드를 다시 읽는다(72~90행). 수강 과목 탭을 열어도
채팅·단어장·문제 기록까지 준비가 끝나야 한다.

**위험:** 커리큘럼/교사 수에 비례하는 fan-out과 채팅 스레드 생성/조회. 홈·수업·교재·
문제 기록·과제·통계·교사 탭의 데이터 경계를 나누고, 채팅/상세 이력은 해당 탭 또는
패널에서만 로드해야 한다.

## 교사 포털

`app/teacher/page.tsx`도 `tab`에 따른 게이팅이 없다. 기본 8개 작업 뒤 교재 라이브러리,
전체 학생 커리큘럼을 순차로 읽고(44~72행), 커리큘럼마다 메모, 학생마다 피드백을
추가로 읽는다(79~100행). 홈이나 가능 시간 탭 진입에도 학생별 커리큘럼·피드백까지
기다린다.

**위험:** 담당 학생/커리큘럼 수에 따라 fan-out이 증가하며, 대시보드가 수업 일정
결과에 의존하는 체인도 존재한다. 홈·수업·가능 시간·학생별 커리큘럼·교재·과제의
SSR 경계를 분리하고, 학생별 상세는 선택 시 읽어야 한다.

## 학부모 포털

`app/parent/page.tsx`는 현재 자녀를 정한 뒤에도 탭과 무관하게 대시보드·예약·수업·
커리큘럼·추천·수업권·동의·정규 진행 희망·모든 자녀의 수강 상태를 한 번에 읽는다
(47~71행). 이후 커리큘럼별 메모와 리뷰·피드백도 추가로 읽는다(75~85행).

다자녀일수록 동의·수업권·모든 자녀 수강 조회는 필요하지만, 홈/예약/레슨 탭을 열 때
계약·동의 상세까지 전부 막아서는 안 된다. 자녀 선택과 동의 URL focus는 보존하되,
홈 핵심 일정과 동의/수업권/레슨 상세의 로딩 경계를 나눠야 한다.

## 시행 순서

1. **P1-우선:** 관리자 사용자 역할별 경량 목록과 매칭 대기 전용 목록. 제품 오너가
   관찰한 15~20초를 첫 실제 행 표시 기준으로 전후 측정한다.
2. **P1-후속:** 예약·문의·면담·종료 요청의 결합 초기 로더와 스켈레톤, 목록 범위 제한.
3. **P1-후속:** 신규(기존 상담) 카드의 최소 요약 우선 표시와 상세 지연 로드.
4. **P1-전수 확장:** 학생 → 교사 → 학부모 순으로 탭별 SSR 경계를 도입한다. 각
   포털에서 현재 탭 외 데이터를 첫 응답에서 제거하고, URL/뒤로가기/앞으로가기/권한
   회귀를 함께 검증한다.

모든 배치는 같은 Preview 계정·동일 데이터 조건에서 첫 스켈레톤 시간, 첫 실제 콘텐츠
시간, 요청 수, 인증 호출 수, 탭 재진입 시간을 각각 보고해야 한다.
