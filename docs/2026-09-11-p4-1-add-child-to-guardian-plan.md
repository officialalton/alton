# P4-1 착수 1장 정리 — 기존 주 보호자 선택 + 자녀 추가 (2026-09-11)

근거: `docs/2026-09-10-p4-1-account-expansion-and-household-archive-investigation.md`
A절 및 "확정 정책 (2026-09-11)". 정책은 확정본이며 여기서 재결정하지 않는다.
범위: A(자녀 추가)만. B(가구 아카이브)·P4-3(관리자 문서 탭)은 이번 라운드 밖.

## 1. 사용자 흐름

- **정상**: 관리자 `신규 > 계정 생성` 탭 → `+ 자녀 추가` → 보호자 검색(이름/이메일)
  → 후보 선택(주 보호자만 노출) → 자녀 1명 입력(이름·이메일·학년·과목) →
  `자녀 추가 안내 발송` → 보호자에게 기존과 동일한 온보딩 안내 메일 1통 →
  보호자가 링크 클릭 → 확인 버튼(POST) → 자녀 Auth 계정 생성 →
  기존 household에 `role='child'`로 추가 → 이후는 자녀 단위 공통 경로
  (자녀 정보 완료 → 보호자 동의 → 교사 매칭 → 체험 Smart Notes 동의 →
  체험 수업권 → 예약 → 수업). 발송 건은 기존 `발송 내역` 목록에 그대로 표시된다.
- **실패(차단)**: 자녀 이메일이 기존 `auth.users`와 중복 → 링크 생성·발송을
  시작하지 않고 자녀 이메일 입력란에 인라인 안내. 실패 링크를 남기지 않는다.
- **실패(발송 오류)**: 링크는 생성됐으나 메일 발송 실패 →
  `notice_delivery_status='failed'` + 오류 배너. 기존 `발송 내역`의 재발급으로 복구.
- **취소**: 폼의 `취소`로 닫으면 아무 것도 생성되지 않는다.
- **재시도**: 중복 이메일을 고쳐 다시 제출(동일 폼). 발송 후 수정은 기존
  `reissueDirectOnboardingLinkAction()`(revoke 후 재발급) 경로를 그대로 쓴다.

## 2. 데이터와 권한

- **신규 상태·테이블·마이그레이션 없음.** 조사 A-6 결론대로 UI + 서버 액션만 추가한다.
- **원본 경로 하나**: 발송은 `sendDirectOnboardingNoticeInternal()`
  (`app/admin/direct-account-actions.ts`) 단일 경로. 새 액션은 보호자 id →
  이메일·이름을 서버에서 해석해 이 함수에 넘기는 얇은 래퍼다. 새 RPC·새 링크
  타입을 만들지 않는다(`create_direct_onboarding_link_multi`, 학생 배열 길이 1).
- **중복 차단**: `lib/onboarding-email-guard.ts`의
  `findExistingAuthEmailCollisions()` 재사용(신규 헬퍼 금지). 보호자 이메일은
  대상 제외(기존 계정 재사용이 정상 흐름).
- **주 보호자 판정 원본**: `households.primary_guardian_id`. 이유는
  `finalize_trial_onboarding_students`의 기존 보호자 분기가 이 컬럼으로만
  가구를 찾기 때문(`20261272000000_...sql:85-89`) — 후보 목록도 같은 기준으로
  만들어 "선택은 되는데 redeem에서 실패"를 원천 차단한다. 공동 보호자
  (`household_members.is_primary=false`)는 후보에 노출하지 않는다.
- **권한**: 두 액션 모두 `requireAdminOrCapability("manage_consultations")`.
  클라이언트가 보낸 보호자 이메일을 신뢰하지 않고 `guardianId`만 받아
  서버에서 `households` + `get_emails_by_user_ids`로 재확인한다.
- **고유 제약**: 기존 `household_members_one_household_per_child`(자녀당 1가구)와
  `unique(household_id, profile_id)` 그대로. 형제자매 행은 읽지도 쓰지도 않는다.

## 3. UAT 데이터

- 실행 ID: `p4-1-add-child-20260911`. 전용 UAT 관리자 계정과 전용 보호자
  1가구(자녀 1명 기생성)를 이 ID로 만든다. 자동 테스트는 `@example.com` +
  타임스탬프 픽스처만 쓰고 UAT 계정과 섞지 않는다(기존 통합 테스트 관례 동일).
- 완료 기준: 시작 전 기존 공식 계정 목록 확인 → 종료 후 실행 ID 단위로
  `transition_account_status()`/`banned_until` 비활성화(삭제하지 않음) →
  공식 계정 보존 확인.

## 4. UI 기준

- `AccountCreationTab`: 기존 버튼 라벨 `+ 계정 생성` → `+ 부모 계정 생성`,
  그 아래 `+ 자녀 추가` 버튼 추가. 탭 설명 문구를 두 진입점 기준으로 수정.
- `AddChildToGuardianForm`:
  - **보호자 검색**: 입력 2자 이상에서 검색(디바운스). 후보 행 = 보호자 이름 /
    이메일 / 기존 자녀 이름. 빈 상태 "검색 결과가 없습니다", 로딩 "검색 중...".
  - **선택 후**: 선택한 보호자 요약 + `변경` 버튼. 자녀 입력 1행(이름·이메일
    필수, 학년·과목 선택) — 행 추가/삭제 없음.
  - **오류**: 중복 이메일은 자녀 이메일 입력란 바로 아래 인라인 + 토스트,
    그 외 실패는 상단 배너 + 토스트. 성공 시 토스트 후 폼 닫기 + 발송 내역 갱신.
  - 발송 버튼은 보호자 미선택·필수값 미입력·발송 중에 비활성.
- 정보 밀도·문구·공통 컴포넌트 정리는 마일스톤 종료 폴리싱 라운드에서 처리.

## 5. 검증과 성능

- **통합/유닛 테스트**: (a) 후보 조회가 주 보호자만 반환하고 공동 보호자를
  제외하는지(psql 통합), (b) 기존 보호자 + 자녀 1명 finalize가 새 household를
  만들지 않고 기존 가구에 자녀만 추가하며 형제자매 행이 불변인지(psql 통합),
  (c) 중복 이메일이면 링크 생성 RPC·메일 발송이 전혀 호출되지 않는지(유닛),
  (d) 권한 거부·보호자 미검증(주 보호자 아님) 거부(유닛),
  (e) 같은 보호자·같은 자녀로 두 번 발송해도 가구·형제자매가 깨지지 않는지(멱등/부분 실패).
- **Preview UAT**: 실제 발송 → 메일 링크 → 확인 버튼 → 자녀 계정 생성 →
  학부모 포털에서 자녀 2명이 보이고, 기존 자녀의 상태(동의·수업권·예약)가
  변하지 않았는지 확인.
- **성능**: 보호자 검색은 왕복 2회 고정(`households`+`profiles` 조인 1,
  `get_emails_by_user_ids` RPC 1)이며 결과 20건으로 제한한다. 기존 탭의
  SSR 쿼리 수는 변하지 않는다(검색은 클라이언트 요청 시에만 발생).
