# P4-2 착수 1장 정리 — 교사 정산 흐름 (2026-09-12)

근거: `docs/2026-09-10-p-execution-roadmap.md` P4-2 절, R10 구현
(`20260830070000_r1_payout.sql`, `20261218000000_r10_payout_batch_lifecycle.sql`,
`20261222000000_r10_settlement_pipeline_schema.sql`, `app/admin/payout-batches-*`).
**범위 밖(고정)**: 실제 송금, `paid` 전이, Mercury/Wise·Stripe Live, Drive 권한·
환경변수 변경. P4-3 관리자 문서 탭 구현도 이번 범위 밖(연계 지점만 만든다).

## 사전 조사 결론 (재사용 대상)

- **정산 원장은 이미 있다**: 세션 최종 판정이 `upsert_session_payout_item()`
  (`20261030000000_m5a_...sql:50`)으로 `payout_items` 1행을 만들고 갱신한다
  (`amount_minor = 시급 스냅샷 × payable_minutes / 60`). 배치는
  `generate_payout_batches(period_start, period_end)`가 **세션 예약일
  (`reservations.starts_at::date`) 기준 월**로 묶는다.
- **교사 읽기 권한도 이미 있다**: `payout_items`/`payout_batches`/
  `payout_batch_audit_log` RLS 조회 정책이 `teacher_id = auth.uid()`를 이미
  허용한다 — **교사 정산 화면에 새 RLS·새 RPC가 필요 없다.**
- **없는 것**: 교사 수취 계좌 테이블, 교사 제출 서류 테이블, Storage 버킷
  (현재 레포에 `storage.buckets` 0개, `storage.from(` 사용처 0곳), 교사 포털
  정산 진입점.
- `payouts-data.ts`(레거시 `payouts` 테이블)는 쓰지 않는다 — v3
  `payout_batches`/`payout_items`만 원본으로 쓴다.

## 1. 사용자 흐름

- **교사(정상)**: 교사 포털 `정산` 탭 → ① 다음 지급 예정액(통화별) ② 월별 정산
  내역(수업 월 · 지급 예정 월 · 상태 · 금액) ③ 월 펼치면 수업별 산출 근거
  (날짜·학생·과목·지급 대상 분·시급 스냅샷·금액) ④ 수취 계좌 등록·수정
  ⑤ 제출 서류 업로드·목록.
- **계좌(실패/재시도)**: 필수값 누락·형식 오류는 인라인 오류로 막고 저장하지
  않는다. 저장 성공 시 마스킹된 값으로 다시 표시한다. 재입력하면 덮어쓰고
  변경 이력이 1행 쌓인다.
- **서류(실패/취소)**: 허용 확장자·크기를 넘으면 업로드 전에 막는다. 업로드
  실패는 메타 행을 남기지 않는다(파일·메타 모두 없음). 취소는 무변경.
  **미제출·검토 상태는 어떤 업무도 차단하지 않는다** — 정산·매칭·수업 어느
  경로에서도 서류 상태를 읽지 않는다.
- **관리자**: `정산` 탭에 `수취 계좌` 서브탭 → 교사별 계좌 목록(마스킹) +
  변경 이력. 값 수정은 교사 본인만 한다(관리자는 조회 전용).

## 2. 데이터와 권한

- **신규(additive migration 1건)**
  - `teacher_payout_accounts` — 교사당 1행(`unique(teacher_id)`):
    예금주, 은행명, 계좌번호, 통화, 국가, (선택) SWIFT/라우팅, 갱신 시각·갱신자.
  - `teacher_payout_account_events` — INSERT-only 변경 이력:
    `action(created|updated)`, 바뀐 필드 이름 목록, 계좌번호 끝 4자리 전/후.
    **이력에는 전체 계좌번호를 복제하지 않는다.**
  - `teacher_documents` — 제출 서류 메타(교사, 종류, 파일명, storage 경로,
    크기, MIME, 업로드 시각). 파일 본문은 비공개 Storage 버킷
    `teacher-documents`에 `<teacher_id>/<uuid>-<파일명>`으로 둔다.
- **권한**: 세 대상 모두 RLS — 교사는 **본인 행만** 읽기·쓰기,
  관리자/`정산권한`은 읽기. Storage 버킷도 같은 규칙(경로 첫 세그먼트가
  본인 `teacher_id`일 때만). 관리자 계약·동의서 권한은 확대하지 않는다.
- **마스킹**: 서버가 계좌번호 전체를 클라이언트로 절대 내려보내지 않는다 —
  교사 본인 화면에도 `****1234` 형태만 내려가고, 수정은 전체 재입력이다.
  관리자 목록도 동일 원본·동일 마스킹을 쓴다.
- **정산 수치 원본 경로 하나**: `payout_items`(+ `payout_batches`)만 읽는다.
  교사 화면은 사용자 스코프 클라이언트로 자기 행만 읽고(기존 RLS),
  금액을 앱에서 다시 계산하지 않는다 — `amount_minor`를 그대로 쓴다.
- **지급 상태 = 4단계(2026-09-12 제품 오너 확정 흐름)**. 앱은 이 어휘로만 말한다.

  | 단계 | 뜻 | 판정 기준(`payout_batches.status`) |
  | --- | --- | --- |
  | 예정 | 최종 판정되어 정산 항목이 생긴 수업의 **실시간 합계**. 예약만 된 미진행 수업은 제외. 재판정·조정으로 변동 가능 | 묶음 없음(`batch_id is null`) |
  | 검토 중 | 정산 대상 월이 끝나 월별 묶음이 생겼고 관리자가 산출 근거·조정 내역·마스킹 계좌를 확인하는 단계 | `draft`/`calculated`/`reviewing`/`reviewed`/`failed` |
  | 송금 승인됨 | 송금 권한 운영자가 실제 지급 대상으로 최종 승인. **사람의 유일한 승인 지점** | `approved`/`dispatch_requested`/`provider_pending`/`processing` |
  | 지급 완료 | 금융사 처리까지 끝남 | `paid` |

  - 승인 이후의 `dispatch_requested → provider_pending → paid`는 **실행 단계**이지
    사람이 다시 판단하는 지점이 아니다 — 교사 화면에서는 `송금 승인됨`으로 묶는다.
    실제 금융 연동을 열 때 거래 ID와 결과로 추적하고, 재시도는 같은 식별값
    (`payout_batches.dispatch_idempotency_key`, 이미 unique)으로 이중 송금을 막는다.
  - `failed`는 실행이 실패해 관리자 손으로 되돌아온 상태라 `검토 중`으로 보여준다.
  - **사람이 예정액을 수기로 계산하거나 임의로 확정하는 경로를 만들지 않는다** —
    금액은 언제나 `payout_items`에서 온다.
  - **마감 뒤 변동**: 수업 판정·금액이 바뀌어도 이미 송금 승인된 금액을 덮어쓰지
    않고 **다음 정산월의 조정 항목**으로 반영한다. DB도 같은 방향으로 이미 잠겨
    있다(`prevent_paid_item_mutation`, `reverse_payout_item()`).
  - `paid` 전이·실제 송금은 이번 범위 밖이며 화면은 읽기만 한다.

## 5. 검증과 성능

- **통합/유닛**: (a) 교사는 본인 payout 행만 읽고 타 교사 행은 RLS로 막힌다,
  (b) 예정/확정/지급 완료 3분류가 배치 상태에 따라 정확히 갈린다,
  (c) 계좌 저장이 변경 이력 1행을 남기고 전체 계좌번호를 응답에 넣지 않는다,
  (d) 교사는 타 교사 계좌·서류를 읽지 못한다(RLS), (e) 서류 상태가 정산 수치
  계산에 전혀 관여하지 않는다(게이트 아님), (f) 관리자 목록이 교사와 같은
  원본을 읽고 동일하게 마스킹한다.
- **Preview UAT**: 위 흐름 1회.
- **성능**: 교사 정산 탭은 왕복 4회 고정(payout_items+batches 조인 1, 세션 근거 1,
  계좌 1, 서류 1) — 수업 수에 비례한 N+1을 만들지 않는다.

## 확정 / 남은 항목 (2026-09-12 제품 오너 회신 반영)

1. **예정액 산정 대상 — 확정**: 최종 판정이 끝나 `payout_items`가 생긴 수업만
   포함한다(예약만 되고 아직 진행되지 않은 수업은 제외).
2. **지급 주기·마감일·지급일**: "수업 월 기준 익월 지급"만 표시하고 구체
   마감일·지급일은 **확정되기 전까지 표시하지 않는다**(2026-09-12 확정).
3. **공제·보류 — 확정**: 세금·수수료·보류 공제를 반영하지 않은 **총액**을
   보여주고 화면에 그렇게 명시한다.
4. **제출 서류 종류 — 확정**: 특정 서류 종류를 강제하지 않는다. W-9/W-8BEN 등도
   고정 목록으로 만들지 않고 **자유 업로드·보관 창구**로 유지한다(종류 enum 추가
   없음). 미제출·검토·승인 상태가 정산·매칭·수업을 차단하지 않는다.

## 2차 구현(2026-09-12) — 자동 월 마감 / 최종 송금액 조정 / 차액 이월

마이그레이션 `20261285000000_p4_2_payout_month_close_and_adjustments.sql`.

### 자동 월 마감

- `close_payout_period(period_start, period_end)` 신설. 정상 경로는 **자동 마감**이고,
  관리자가 기간을 넣어 실행하는 `generate_payout_batches()`는 **운영 보조 수단**으로
  남긴다(`closePayoutMonthNow()`가 같은 자동 마감 경로를 수동으로 한 번 더 돌린다).
- 진입점: `GET /api/cron/close-payout-month`(`vercel.json` cron `0 3 1 * *`).
  **fail-closed** — `CRON_SECRET`이 없으면 503으로 아무것도 하지 않는다. 스케줄
  등록과 실제 활성화를 분리하기 위함이다(실제 송금 게이트와 같은 취지).
- **중복 실행·실행 지연·월 경계 재시도 안전성**(3중):
  1. 기간 단위 `pg_advisory_xact_lock` — 같은 기간 동시 마감을 직렬화.
  2. 후보 항목 `FOR UPDATE ... SKIP LOCKED` — 같은 항목을 두 호출이 동시에 후보로
     삼지 못한다(기존 `20261263000000` corrective와 같은 장치).
  3. **열린 같은 기간 묶음 재사용** — 재실행 시 새 묶음을 만들지 않고 새 항목만
     덧붙인다. `update ... where batch_id is null`로 이미 묶인 항목은 건드리지 않는다.
- **날짜 기준: UTC**(조사 결과 기존 정산이 이미 UTC였다 —
  `reservations.starts_at::date`(DB 타임존 UTC)와 `previousMonthRange()`). 기준을
  바꾸면 월 경계 수업이 다른 달로 재분류되므로 일관성을 위해 유지했다.
  **임의의 지급일은 UI에 표시하지 않는다.**

### 최종 송금액 조정

- `add_payout_batch_adjustment(batch, amount, reason, actor)` 신설.
  **수업별 `payout_items` 금액과 자동 산정 근거를 고치지 않는다** — 별도 조정
  항목(`item_type='adjustment'`, `session_id is null`)을 추가하고, 사유·처리자·시각은
  `payout_batch_adjustments`(INSERT-only)에 남긴다.
- 허용 시점: 검토 중에는 그대로. **승인 뒤 송금 요청 전이면 묶음을 `reviewed`로
  되돌리고 `approved_at`을 지워 재승인을 요구한다**(감사 로그 `reverted_to_review`).
  **송금 요청 이후(`dispatch_requested`/`provider_pending`/`processing`/`paid`)에는
  거부**하고 "차액은 다음 정산월 조정 항목으로" 안내한다.
- 화면 값: 자동 산정 수업 합계 / 가감액 / 최종 금액을 교사·관리자 모두 분리해 본다.

### 마감 뒤 차액 이월

- `upsert_session_payout_item()` 보완. 기존에는 `batched` 항목도 제자리 갱신해
  **이미 승인된 묶음의 금액이 조용히 바뀔 수 있는 구멍**이 있었다.
  - 묶음 없음 / 아직 열린 묶음(검토 중) → 기존대로 제자리 갱신(검토 정확도 유지)
  - **승인 이후 묶음 → 원본 불변**, 차액만 미배치 조정 항목으로 생성하고
    `adjusts_payout_item_id`로 원본과 연결
  - 무지급 판정으로 바뀌면 원본을 지우지 않고 전액 차감 조정 항목을 만든다
- 그 미배치 조정 항목은 **다음 `close_payout_period()`가 자동으로 싣는다**
  (세션 기반 항목과 함께 한 번의 잠금 스캔으로 후보에 포함).

### 여전히 범위 밖

- 실제 송금, 금융 제공자 호출, `dispatch_requested`/`provider_pending`/`paid` 전이는
  `real_disbursement_enabled()` 게이트가 닫혀 있어 도달 불가다. **이번에 열지 않았다.**
- Production 변경 없음. cron은 `CRON_SECRET` 없이는 동작하지 않는다.


## 3차 — Preview UAT 피드백 반영 (2026-09-12)

### 관리자 포털

- **목록이 사라지던 버그 수정(실제 결함)**: `PayoutBatchesTab`이 SSR `initialBatches`를
  `useState` 초기값으로만 썼는데, 관리자 탭 전환이 클라이언트 라우팅이라 탭을 처음
  마운트할 때 빈 배열을 잡고 그대로 굳었다. 마운트 시 `listPayoutBatchesAction()`으로
  직접 조회하도록 바꿨다(갱신도 전체 새로고침 대신 목록 재조회).
- **`월 마감 실행` 버튼 노출**: 자동 마감(크론)과 **같은 경로**를 수동으로 돌린다.
  기존 `Batch 생성`은 `Batch 생성(구경로)`로 이름을 바꾸고 차이를 화면에 설명했다
  (구경로는 열린 묶음을 재사용하지 않아 같은 기간에 묶음이 또 생길 수 있다).
- **묶음 삭제 추가**(`delete_payout_batch()`): 승인 전(검토 단계)만 허용하고,
  수업 항목은 지우지 않고 **미배치(pending)로 되돌려** 다음 마감에 다시 잡히게 한다.
  **조정 내역이 있는 묶음은 거부**한다 — 조정 이력은 INSERT-only 감사 기록이라
  지울 수 없고, 조정이 붙었다는 건 이미 사람이 판단을 시작했다는 뜻이다.
  되돌리려면 반대 금액으로 다시 조정한다.
- **`검토 제출`·`실패 처리` 설명 추가**: 둘 다 기능은 그대로 두고 무엇을 하는
  버튼인지 화면에 적었다. 실패 처리는 송금 실패를 기록하는 운영용이며 금액을
  바꾸지 않는다.

### 질문에 대한 답(설계 확인)

- **관리자 `검토 제출`과 교사 `검토 중`이 겹쳐 보이는 이유**: 교사에게는 "묶음이
  생겼고 아직 승인 전"이 전부 `검토 중` 하나다(초안/검토 중/검토 완료를 구분해
  보여줄 이유가 없다). 관리자만 그 안을 3단계로 본다 — 의도된 설계다.
- **차액 이월의 기준 시점은 `지급 완료`가 아니라 `송금 승인`이다.** 승인 전에는
  제자리 갱신, 승인 뒤에는 원본 고정 + 차액 이월. 사람이 "이 금액으로 보낸다"고
  결정한 순간부터 숫자를 고정하는 것이 목적이다.


## 4차 — UAT 2차 피드백 (2026-09-12)

마이그레이션 1건 추가(`20261287000000_p4_2_payout_batch_delete_with_adjustments.sql`).

1. **계좌번호 안내 문구 확정**: "띄어쓰기 없이 하이픈(-)을 넣어서 작성해주세요.
   예: 1002-123-456789".
2. **조정이 있어도 승인 전 묶음은 삭제 가능(정책 변경)**. 직전 라운드는 감사 이력
   보존을 이유로 거부했으나 제품 오너 판단으로 뒤집었다. 대신 감사 성격은 유지한다 —
   `payout_batch_adjustments`는 평시 UPDATE·DELETE 모두 금지이고, `delete_payout_batch()`가
   트랜잭션 안에서 세우는 플래그(`app.payout_batch_delete`)가 있을 때만 DELETE가 열린다.
   묶음이 사라지면 그 조정은 가리킬 대상이 없어지기 때문이다. **승인 이후 묶음은 여전히
   어떤 경로로도 삭제 불가.**
   - **관리자 조정**은 묶음과 함께 사라진다(그 묶음에 대한 판단이므로 이월하지 않는다).
   - **마감 뒤 재판정으로 생긴 이월 조정**은 살아남아 미배치로 돌아가 다음 마감에 잡힌다.
3. **묶음 생성만으로 교사 화면이 '검토 중'이 되지 않는다**: `draft`/`calculated`는
   계속 **예정**이고, 관리자가 `검토 제출`을 눌러 `reviewing`이 된 뒤부터 **검토 중**이다.
4. **지급 일정 표기를 상태별로 분리**: 요약 카드에 "매월 10일에 전월 수업분을 지급합니다"를
   일반 안내로 올리고, 월별 행은 예정 → `지급 예정일 …`, 검토 중 → `검토 완료 후 지급
   (예정일 …)`, 지급 완료 → 실제 지급일. 검토 중인데 날짜만 보이면 그 날짜가 지난 뒤
   지급 시점을 오해하게 되기 때문이다.

### 확인된 사실 — 지급 일정은 아직 "표시"일 뿐이다

제품 오너 질문("승인하면 송금이 어떻게 작동하나")에 대한 실측 확인 결과를 남긴다.

- **`payout_batches`에 지급 예정일 컬럼이 없다.** 10일은 `payoutDateOf()`가 수업 월
  기준으로 화면에서 계산하는 값이고, 그 날짜에 실행되는 잡도 저장되는 값도 없다.
- **승인은 아무것도 촉발하지 않는다.** `approved` + `approved_at` 기록이 전부다.
- 송금 체인(`dispatch_payout_batch` → `mark_payout_batch_provider_pending` →
  `mark_payout_batch_paid`)은 **DB에 이미 있고 전부 `real_disbursement_enabled()`
  게이트를 먼저 확인한다**(현재 false). **앱에는 호출 경로가 없고**(서버 액션 미작성),
  Mercury/Wise 클라이언트 코드도 레포에 없다. 재시도 안전장치는 배치 단위
  `dispatch_idempotency_key`(unique)와 항목 단위 `provider_transaction_id`/
  `failure_reason`/`retry_count`로 이미 준비돼 있다.

### 그래서 남은 결정 3건 (금융 연동 착수 전)

1. **10일에 누가 dispatch를 부르나** — 관리자 수동 버튼인가, 10일 크론이 `approved`
   묶음을 자동 dispatch하는가. 현재 어느 쪽도 없다.
2. **승인이 10일을 넘겼을 때** — 지금은 수업 월 기준 계산이라 화면에 여전히 그 달 10일이
   뜬다. 다음 10일로 미룰지, 승인 즉시 보낼지 규칙이 필요하다.
3. **지급 예정일을 데이터로 남길지** — 알림·리포트·문의 대응을 하려면
   `payout_batches.scheduled_payout_date` 같은 컬럼이 필요하다. 계산값으로 두면 규칙이
   바뀔 때 과거 건의 표시도 함께 바뀐다.
