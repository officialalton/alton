# ALTON 제품 분석 도입 PRD

## 1. 배경과 문제

ALTON은 랜딩 페이지, 상담 신청, 가입·온보딩, 학생·학부모·컨설턴트·교사 포털을 제공한다. 현재 방문자가 어디에서 유입되고 상담 신청·가입으로 이어지는지, 핵심 서비스 흐름을 실제로 사용하는지, 실제 사용자 환경에서 성능 문제가 있는지 일관되게 측정하지 못한다. 대학 탐색은 서비스의 한 기능이며 분석 체계의 중심 전환으로 다루지 않는다.

랜딩 출시와 초기 운영에서는 최소한의 익명 웹 분석과 핵심 전환 이벤트가 필요하다. 다만 학생·학부모의 개인정보, 상담 기록, 에세이, 수업 및 성적 데이터는 분석 도구로 전송하면 안 된다.

## 2. 목표

1. 랜딩 페이지의 방문, 유입 경로, 주요 페이지 성과를 출시 직후 확인한다.
2. 상담 신청, 가입·온보딩, 수업·상담·메신저 등 핵심 서비스 흐름을 익명 이벤트로 측정할 기반을 만든다.
3. 실제 사용자 환경의 페이지 성능을 확인하고 개선 우선순위를 정한다.
4. 분석 데이터에 PII 또는 교육·상담 콘텐츠가 들어가지 않도록 보장한다.

## 3. 범위

### P0 — 이번 출시

- Vercel Web Analytics 연결
- Vercel Speed Insights 연결
- 아래 전환 이벤트의 익명 수집
  - `landing_cta_clicked`
  - `consultation_started`
  - `consultation_submitted`
- 환경 분리: production만 실제 지표 집계. local/preview/test는 기본 비활성화한다.
- 개인정보 차단 규칙과 이벤트 명세 문서화

### P1 — 초기 운영 후

- PostHog 또는 GA4 중 하나를 제품 이벤트 도구로 도입
- 상담 신청 퍼널: 유입 → CTA → 신청 시작 → 제출 → 상담 확정
- 가입·온보딩 퍼널: 가입 시작 → 초대 확인 → 계정 생성 → 첫 서비스 진입
- 서비스 활성화: 상담 예약, 수업 입장, 메시지 발송, 과제 제출 등 핵심 행동
- 운영용 주간 대시보드와 지표 검토 루틴

### P2 — 이후 검토

- 사용자 코호트, 역할별 기능 리텐션, 실험(A/B test)
- 광고 캠페인 귀속 및 CRM 연동
- 세션 리플레이: 별도 개인정보 검토와 마스킹 설계가 끝난 뒤에만 검토

## 4. 비목표

- 상담 메시지, 에세이, 과제, 수업 녹화, 성적, 업로드 문서의 내용 분석
- 이름, 이메일, 전화번호, 생년월일, 학교, 가구 ID를 분석 도구로 전송
- preview/non-prod의 테스트 데이터를 운영 대시보드에 섞는 것
- 이번 단계에서 광고 성과 분석 또는 세션 리플레이 도입

## 5. 사용자 스토리

- 마케팅 담당자로서 랜딩 유입과 상담 전환을 보고, 효과적인 유입 채널을 판단하고 싶다.
- 제품 담당자로서 상담 신청, 가입·온보딩, 실제 서비스 사용에서 사용자가 이탈하는 지점을 알고 싶다.
- 엔지니어로서 실제 사용자 환경에서 느린 페이지와 Core Web Vitals 문제를 확인하고 싶다.
- 학생과 학부모로서 서비스 이용 정보가 분석 목적으로 과도하게 수집되지 않기를 원한다.

## 6. 이벤트 명세

모든 이벤트 공통 속성:

- `event_name`
- `surface`: `landing | college_explore | consultation`
- `locale` (예: `ko`, `en`)
- `page_path` (쿼리스트링 제거)
- `referrer_domain` (가능한 경우)
- `deployment_environment`: production만 수집

허용 가능한 추가 속성:

| 이벤트 | 추가 속성 |
| --- | --- |
| `landing_cta_clicked` | `cta_name`, `section` |
| `consultation_started` | `entry_point` |
| `consultation_submitted` | `entry_point`, `consultation_type` |

금지 속성:

- 사용자 ID, household ID, 이메일, 전화번호, 이름
- 상담 신청 본문, 메시지, 에세이, 문서 제목·내용
- 성적, 시험 점수, 지원 대학 목록, 컨설턴트 메모
- 원본 URL query string 또는 URL fragment

## 7. 기능 요구사항과 출시 기준

### Vercel Web Analytics

- production 배포에서만 로드된다.
- 랜딩, 상담 신청, 공개 안내 페이지 조회가 Vercel 대시보드에서 확인된다.
- preview와 local에서는 운영 지표에 유입되지 않는다.

### Vercel Speed Insights

- production에서 Core Web Vitals를 수집한다.
- 랜딩 Hero, 상담 신청, 로그인·온보딩 등 유입과 전환에 직접 연결되는 화면을 초기 모니터링 대상에 포함한다.

### 커스텀 전환 이벤트

- 한 번의 사용자 행동에 동일 이벤트가 중복 기록되지 않는다.
- CTA 클릭과 실제 상담 제출은 별도 이벤트다.
- 상담 제출 실패 시 `consultation_submitted`를 보내지 않는다.
- 개인정보 금지 목록을 이벤트 payload 테스트로 검증한다.

## 8. 구현 원칙

1. 공통 분석 모듈 한 곳에서 이벤트를 정의하고 호출한다.
2. 컴포넌트에 도구별 호출 코드를 흩뿌리지 않는다.
3. production 여부를 서버/클라이언트 환경 변수로 명확히 제어한다.
4. 이벤트 명칭과 속성은 이 문서의 명세를 변경 승인 없이 바꾸지 않는다.
5. 분석 도구 장애가 사용자 기능, 상담 제출, 로그인에 영향을 주면 안 된다.

## 9. 성공 지표

출시 후 30일 기준:

- 랜딩 핵심 CTA 클릭률을 확인할 수 있다.
- 상담 신청 시작 대비 제출 완료율을 확인할 수 있다.
- 가입·온보딩 단계별 완료율을 이후 확장 시 확인할 수 있다.
- 주요 공개 화면의 Core Web Vitals 추이를 확인할 수 있다.
- 분석 이벤트에서 PII가 발견되지 않는다.

초기에는 목표 수치보다 기준선(baseline)을 확보하는 것을 우선한다. 기준선 확보 후 월간 목표치를 정한다.

## 10. 운영 방식

- 매주: 유입, CTA 클릭, 상담 시작/제출, 성능 이상을 검토한다.
- 매월: 유입 채널·랜딩 섹션·상담 신청과 온보딩 완료율을 바탕으로 UX 개선 항목을 선정한다.
- 분기별: 이벤트 목록과 개인정보 규칙을 점검한다.

## 11. 결정 사항

- P0 분석 도구: Vercel Web Analytics + Vercel Speed Insights
- 제품 전환 분석 도구: P1에서 PostHog와 GA4 중 하나를 선정
- 세션 리플레이: 이번 범위 제외
- 실제 사용자의 개인 학습·상담 데이터: 분석 이벤트 전송 금지
