# 유형별 문제 품질 계약 — 세부 기술 30개 (2026-09-15)

목적은 정상 문제를 제한하는 것이 아니라 **질문·자료·정답·학생 화면의 연결 오류를 생성 단계에서 없애는 것**이다. 코드: `lib/problem-quality-contract.ts`(계약·검사), `lib/problem-generation/review.ts`(독립 품질 검사), `lib/problem-generation/pipeline.ts`(생성 → 자료 → 계약 → 독립 검사 → 재생성), `lib/problem-generation/core.ts`(생성기, 인증 없음 — 서버 액션과 표본 배치가 같은 경로).

## 0. 공통 계약

| 연결 | 정의 | 검사 | 실패 시 |
|---|---|---|---|
| 1 질문 대상 | 학생이 무엇을 판단·계산·선택해야 하는가 | `question` 이 따로 있고 유형별 표준 문구/물음 문장 | 저장 안 함 → 사유 피드백 재생성 |
| 2 자료 안의 근거 | 대상이 지문 / Text 1·2 / 메모 / 표 / 그래프 / 도형 / 수식 중 어디에 있는가 | 자료 판정(필수/권장/불필요)·RW 구조 검사·자료 참조 검사(`ref_missing/mismatch`, `unit_missing`) | 자료 재생성 → 재검사 → 재생성 |
| 3 학생 화면 표시 | 빈칸·밑줄·인용 단어 밑줄·Text 구역·메모 목록·자료 렌더·도형 라벨·그래프 객체·선택지 그림 | 대상이 정확히 하나로 식별되는가(빈칸 1, 밑줄 1, 인용 단어 1회, 라벨 충돌·잘림 없음) | 재생성 |
| 4 정답 근거 | 정답이 자료·질문과 실제로 맞고 자료에서 노출되지 않는가 | 유형별 연결(정답 수치 ↔ 자료 값, 정답 ↔ 메모, 정답 문장이 지문에 그대로 없음, 선택지 좌표 점 금지) + **독립 품질 검사**(정답 표시 없이 풀어 지정 정답과 대조) | 불일치면 저장 안 함 |
| 5 답안 형식 | 객관식 A)~D) 4개 / SPR 정규화 가능한 정답 집합 / 로마숫자 조합 | 선택지 4·정답 자리·중복·`x =` 표기·단위 기호, SPR 정수·소수·분수 5/6자, 진술 ↔ 조합 정합 | 저장 안 함 |
| 난이도 | 추론 단계 수·종합 정도·핵심 관계의 미묘함·오답이 정답과 공유하는 정보·자료 해석 부담 (지문 길이·어휘 아님) | 생성기 `difficulty_rationale` + 독립 검사 `estimated_difficulty` → `추정 난이도`. 요청 hard 인데 추정 easy 면 재생성. 학생 응답(`problem_response_stats`)이 쌓이면 `보정 난이도` | 검토 필요 표시 |
| 오답 품질 | 정답 외 각 선택지에 학생에게 보이지 않는 오답 근거(그럴듯한 이유·일부 일치 정보·정답 아닌 이유·유형) | 생성기 `distractor_rationales` + 독립 검사가 obvious/irrelevant 판정. **어려움**: 무관·명백 오답 하나도 불허. **보통·쉬움**: 정답이 사실상 노출되는 경우(무관 2개 이상 또는 셋 다 명백)만 재생성, 그 외는 '쉽게 지워지는 오답'으로 검토 필요 기록 | 재생성 |

학생 화면은 선택지를 **A) B) C) D)** 로 표시한다.

R&W 난이도·오답 기준(Central Ideas·Inferences·Text Structure·Command of Evidence 특히): 정답은 지문의 핵심 관계를 정확히 종합, 각 오답은 지문 일부를 맞게 반영하되 핵심 관계 하나를 빠뜨리거나 잘못 해석. 무관·명백한 반대·과장만의 오답은 생성 실패. hard 는 여러 문장·자료 관계를 종합해야 하고 오답은 각각 일부만 포착.

## C. 독립 품질 검사·오답 자리별 보정·단계형 어려움 생성 (2026-09-15 2차 갱신 — "보강 대기는 좁게, 오답 수정은 자리 하나씩")

- 독립 검사는 생성 모델과 별도 호출. 입력: 지문/자료(대체 설명)·진술·질문·선택지(정답 표시 없음), 유형, 요청 난이도, (어려움이면) 생성기가 미리 낸 설계. 출력: 고른 정답, 확신, 오답별 근거·유형·obvious, 추정 난이도·근거, 설계-문항 정합 여부를 포함한 지적(flags).
- **오답 수정은 자리 하나씩, 계획을 먼저 세운 뒤 생성한다.** "이 오답을 고쳐라"는 자유 지시를 쓰지 않는다. 실패한 선택지마다 `repairOneDistractorCore` 한 번의 호출에서 먼저 구조화된 계획(유지할 지문 근거·자료 값, 학생이 빠질 구체적 오개념, 그 오개념이 정답처럼 보이는 이유, 실제로 틀리는 지점, 다른 세 오답과 겹치지 않는 오류 유형)을 세우고, 그 계획을 반영한 선택지 문장 하나만 함께 받는다. 정답·다른 선택지와의 중복은 문자열 정규화로 결정적으로 검사한다(겹치면 실패 처리). **한 번의 호출로 네 오답을 통째로 고치지 않으며, 자리 하나당 수정 시도는 최대 2회**(전체 문항이나 모든 선택지에 걸쳐 2회가 아니라, 실패한 자리 각각 독립적으로 최대 2회)다. 빈칸 개수·자료 참조·수식 미닫힘·선택지 개수처럼 범위가 명확한 계약 실패는 여전히 필드 단위로만 고친다(`repairFieldsCore`, 결정적 보존).
- **오답 자리별 보정 뒤에도 오답 품질만 남으면(정답·난이도·기타 지적은 문제없음), 그리고 잔여 실패가 정확히 하나 또는 둘의 오답에 한정될 때만** '오답 보강 대기'(`repair_status='needs_distractor_repair'`)로 저장한다. 그 밖의 실패(오답 문제가 셋 이상 남거나, 정답 불일치·설계 불일치·난이도 미달 같은 구조적 문제가 함께 있는 경우)는 대기함에 넣지 않고 **폐기**한다(사유만 로그에 남기고 저장하지 않음) — 구조적 실패에만 전체 재생성이 남는다(어려움 2회·그 외 1회). **보강 대기는 한 번의 요청에서 요청 수를 넘길 수 없고, 목표는 요청 수의 10% 이하다**; 한도를 넘는 후보는 "대기 한도 초과"로 폐기된다.
- **어려움 문항은 생성 자체를 단계로 나눈다.** 위험 문항(어려움 난이도, 또는 독립 검사가 오답의 명백함·무관함·중복 위험을 잡은 문항, 또는 그림·표·복수 지문처럼 자료 관계가 복잡한 문항)만 `문항 설계 → 지문·질문·정답(오답 없이) → 오답 자리별 생성·검사 → 선택지 순서 섞기 → 독립 풀이 검사` 순서를 거친다. 그 밖의 쉬움·보통 문항은 기존처럼 선택지 4개를 한 번에 생성한 뒤 계약·결정적 검사만 적용해 불필요한 추가 모델 호출을 만들지 않는다. `design` 필드(핵심 관계 2~3개·정답이 그 관계를 만족하는 방식·오답별 오류 유형·목표 난이도 근거)는 유지하되, 지문·질문·정답·오답 넷을 한 응답에 길게 요구하지 않는다.
- 관리자 검수 예외는 일반 초안과 분리된다. `repair_status='needs_distractor_repair'` 초안은 기본 '생성' 목록·자동 구성 후보·공개 목록에 나오지 않고, 별도 **'오답 보강 대기'** 탭에서만 보인다. 그 탭에는 실패한 선택지·독립 검사 의견(그럴듯한 이유·일부 일치·틀린 이유·유형)·수정 방향이 표시된다. 관리자가 오답을 고쳐 초안 저장한 뒤 '다시 검사'를 눌러 통과해야만 `repair_status='none'`(일반 초안)으로 바뀐다. 통과하지 못하면 공개·자동 구성·학생 화면에 절대 들어가지 않는다.
- **수치는 분리해 보고한다** — 절대 하나로 뭉뚱그리지 않는다: 첫 생성 통과율(보정 0회로 통과한 후보 수 / 게이트를 거친 전체 후보 수), 자동 보정 뒤 최종 통과율(채택 수 / 요청 수), 보강 대기 전환율(대기 수 / 요청 수, 목표 ≤10%), 유형별·실패 사유별 비율, 문항당 평균 모델 호출 수. "N개 요청 → M개 후보 평가" 형태로 요청과 후보(재생성으로 늘어난 시도 포함)를 구분해 표기하고, 보강 대기 건수를 통과(운영 성과)로 세지 않는다. 빈 응답 이벤트(원인·재시도 결과)와 요청보다 적게 반환된 경우(유형·사유)는 별도로 집계해 화면·보고서에 명시한다.
- 기록: `problem_versions.quality`(계약·추정 난이도·근거·오답 근거·독립 검사·검토 필요) + `repair_status`. 관리자에게는 **난이도 추정 근거**·**검토 필요**·**오답 보강 대기 여부**만 보인다.
- 보정: `problem_response_stats` 뷰(버전별 응답 수·정답률·선택지별 선택 수, 개인 식별 없음)가 관리자 목록에 응답·정답률로 보인다. 응답이 충분히 쌓인 뒤(기준 30건, 별도 결정) `보정 난이도` 로 바꾸고 `calibrated=true` 를 켠다. 그 전까지는 모두 `추정치`.

### D-1. 1차 배치 — 보통 난이도, 30유형 × (단건 1 + 복수 2) = 90건 (`docs/2026-09-15-problem-quality-batch-medium.md`)

- 통과 61/90(68%) · 재생성 94회(해소 19) · 검토 필요 21 · 소요 약 75분.
- 실패 단계: 독립 검사 100건(해소 16), 계약 69건(해소 3). 반복 사유 상위:
  1. 선택지 5개(RW, 12건) — 프롬프트에 "정확히 4개" 강조로 대응.
  2. 독립 검사 정답 불일치(27건) — 생성 오류와 검사 오류가 섞여 있어 **2차 독립 검사**를 두고, 2차가 일치하면 '검토 필요'로 통과, 둘 다 불일치면 저장 안 함.
  3. 오답 "무관/너무 명백"(RW 다수) — 1차 판정은 보통 난이도에도 어려움 기준을 적용해 과하게 걸렀다. 지시대로 **어려움만 무관·명백 오답 불허**, 보통·쉬움은 정답이 사실상 노출되는 경우(무관 2개 이상 또는 셋 다 명백)만 재생성하고 나머지는 '쉽게 지워지는 오답'으로 검토 필요에 기록.
  4. 좌표평면 참조 불일치·라벨 겹침, 방위 표현, 빈칸 0개, 진술 없이 로마숫자 선택지, 입체 kind 불일치, 수식 `$` 미닫힘 — 계약이 의도대로 막았고 재생성 해소율이 낮아(3/69) 사유 피드백 문구를 구체화할 대상.
- 유형별 0/3: Inferences, Command of Evidence (Textual), Rhetorical Synthesis — 선택지 5개·오답 판정 과엄격이 겹친 결과. 아래 2차 배치에서 재확인.

### D-2. 2차 배치 — 판정 보정 뒤 약한 유형 12개 재실행 (`docs/2026-09-15-problem-quality-batch-medium-rerun.md`)

(2) 좌표평면 지문의 방위 표현(4)·라벨 겹침 — 계약이 막았고 재생성 문구 구체화 대상. (3) 입체 kind 불일치(6) — 복합 입체(원뿔+원기둥) 문항 시도. (4) 표 참조 검사 오탐 1건("Month 2 … Month 3" 두 행을 부르는 절) — 검사 수정.

### D-3. 3차 배치 — 어려움 난이도, 8유형 × 3 = 24건 (`docs/2026-09-15-problem-quality-batch-hard.md`)

- 통과 4/24(17%). 어려움 기준(무관·명백 오답 하나도 불허, 추정 난이도 hard)은 제품 오너 지시대로 엄격하며, 당시 생성기는 이 기준을 대부분 통과하지 못했다 — "지문 길이·어휘만 어렵고 오답이 쉽게 지워지는" 문항이 대다수였다는 뜻이다.
- 조치(1차): 스키마에 객관식 선택지 `minItems/maxItems 4` 강제, 어려움 재생성 2회, 오답 유형 다양화 규칙 → 같은 6유형 재실행 61%(`hard-rerun.md`).
- 조치(2차, 제품 오너 "1→2→4 순서로 진행"): **부분 수정을 기본 경로로**(오답만 걸리면 그 자리만 수정, 범위 명확한 계약 실패는 필드만 수정), **어려움 오버샘플링**(N+2개 생성 후 통과분 채택), **어려움 설계 우선**(핵심 관계·오답 오류 유형을 먼저 정하고 지문 작성), **오답 보강 대기함 분리**(부분 수정으로도 안 되는 오답 전용 문제는 전체 재생성 대신 별도 대기함, 일반 초안·자동 구성·공개에서 숨김) → 같은 6유형 재실행 22%(`hard-rerun2.md`, `design` 필드 추가 직후 — RW 유형에서 "AI 응답에 문제가 없습니다"가 급증, 토큰 예산 부족으로 판명).
- **버그 수정**: 어려움 문항은 `design` 필수 필드 때문에 응답이 길어져 고정 `max_tokens: 4000` 을 넘겨 도구 호출이 잘리고 `problems` 배열이 통째로 비어 돌아왔다. 난이도·개수에 비례해 토큰 예산을 늘리도록 고쳤다(최대 8000).
