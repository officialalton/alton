## 1. 이 문서의 권한

이 문서는 2026-08-29 이전에 작성된 문서 중 Calendly, Zoom, DocuSign, Google Drive, Google Docs, 예약 방식, 계정 생성 시점과 관련된 결정보다 우선한다.

기존 문서는 다음 용도로만 사용한다.

- `docs/spec/functional-spec.md`: 사업 배경과 세션뷰 원칙 참고
- `docs/tickets.md`: 지금까지의 개발 이력 참고
- `docs/2026-08-29-진행내역-정리.md`: 당시 배포 개발본 상태의 스냅샷
- 기존 목업: UI 의도 참고. 데이터 구조나 외부 서비스 결정의 기준으로 사용하지 않음

새 구현이 이 문서와 충돌하면 코드를 작성하기 전에 의사결정을 다시 확인한다. 임의로 기존 문서를 선택해 구현하지 않는다.

## 2. 목표

Alton의 핵심 교육 경험은 자체 서비스에 유지하면서, 예약·화상회의·회사 문서처럼 이미 검증된 범용 기능만 Google Workspace에 맡긴다.

이번 개편의 성공 기준은 다음과 같다.

1. 상담 신청부터 정규 수업까지 모든 상태를 Alton에서 추적할 수 있다.
2. 학생이 예약하면 Alton과 Google Calendar에 동시에 일관되게 반영된다.
3. 선생님이 늘어나도 개인 Calendly/Zoom 계정을 별도로 연결하지 않는다.
4. 기존에 완성된 세션뷰·학생 포털·커리큘럼·결제·채팅을 다시 만들지 않는다.
5. 운영자가 외부 서비스 대시보드를 순회하지 않아도 주요 상태를 알 수 있다.

## 3. 최상위 원칙

> Google Workspace는 업무 인프라이고, Alton/Supabase는 업무 상태의 원본이다.

```text
학생·학부모·선생님·관리자
             │
          Alton 웹앱
             │
   ┌─────────┴───────────┐
   │                     │
Supabase              Google Workspace
업무 상태의 원본        외부 업무 인프라
   │                     │
학생/상담/수업/예약      Calendar: 일정 반영
과제/리뷰/크레딧         Meet: 수업 링크
채팅/필기/화이트보드     Drive: 회사 문서
권한/감사 이력           Docs: 외부 공동편집
   │
Stripe: 결제
```

Google 일정이나 파일이 삭제되어도 Alton의 수업·계약·결제 기록이 함께 사라지면 안 된다. Google의 식별자는 Alton DB가 보유하는 외부 참조값이다.

## 4. 시스템별 책임

| 영역 | 기준 시스템 | 역할 |

| 상담·온보딩 상태 | Supabase | 신청, 예약, 상담 완료, 체험, 계약 전환 추적 |
| 선생님 수업 가능 시간 | Supabase | 반복 가능 시간과 날짜별 예외 저장 |
| 실제 일정 충돌 | Google Calendar FreeBusy | 선생님의 기존 일정과 충돌하는 슬롯 제거 |
| 예약 상태 | Supabase | 예약·취소·재예약·노쇼의 원본 |
| 캘린더 이벤트 | Google Calendar | 확정된 예약의 외부 일정 사본 |
| 화상회의 | Google Meet | Calendar 이벤트마다 새 Meet 링크 생성 |
| 세션뷰·교재·과제·AI | Alton/Supabase | 기존 구현 유지 |
| 교재 필기·화이트보드 | Alton/Supabase Realtime | 기존 구현 유지 |
| 인앱 메시지 | Alton/Supabase | Gmail로 이전하지 않음 |
| 결제 | Stripe | 기존 구현 유지 |

| 전자서명 | Google eSignature(파일럿) | 관리자 수동 발송·수동 완료 확인 |

## 5. 승인된 의사결정

### ADR-001 — 기존 앱을 유지하고 부분 개편한다

- 전면 재개발하지 않는다.
- 학생 포털, 세션뷰, 커리큘럼, 채팅, Stripe, AI 기능을 유지한다.
- 외부 서비스와 연결된 경계만 교체한다.

### ADR-002 — Calendly와 Zoom을 제거한다

- 상담 및 수업 예약 UI는 Alton 안에서 자체 구현한다.
- Google Calendar API로 일정과 Meet 링크를 생성한다.
- 신규 예약에서 Calendly URL, 웹훅, Zoom 링크를 사용하지 않는다.
- 기존 데이터 컬럼은 마이그레이션 기간 동안 읽기 전용 호환용으로 남길 수 있다.

### ADR-003 — Google Workspace 계정은 운영 계정이다

- 관리자와 활동 중인 선생님에게 `alton.education` Workspace 계정을 발급한다.
- 서버는 최소 권한의 domain-wide delegation으로 해당 계정의 Calendar/Drive 작업을 수행한다.
- Workspace 계정 발급과 Supabase 역할 부여는 별도 상태로 추적한다.
- 선생님 퇴사·계약 종료 시 Workspace 접근 회수 절차가 있어야 한다.

### ADR-004 — Supabase 인증은 당장 교체하지 않는다

- 예약 개편과 로그인 개편을 한 번에 수행하지 않는다.
- 현재 이메일/비밀번호 인증을 유지해 변경 범위를 제한한다.
- Google SSO는 예약 시스템이 안정화된 후 별도 의사결정과 마이그레이션으로 진행한다.
- 학생·학부모는 Google Docs 사용을 위해 외부 공유가 가능한 Google 계정을 등록한다. 학교 관리 계정의 외부 공유가 막힐 수 있으므로 개인 Gmail을 권장한다.

### ADR-005 — 선생님 가능 시간은 Alton이 관리한다

- Google FreeBusy는 바쁜 시간만 제공하므로 수업 가능 시간의 원본으로 사용하지 않는다.
- 선생님은 Alton의 `일정 오픈` 화면에서 반복 가능 시간과 예외를 설정한다.
- 학생에게 보이는 슬롯은 `Alton 가능 시간 - Google busy - 기존 예약`으로 계산한다.

### ADR-006 — 예약은 자동 확정한다

- 선생님이 공개한 가능 시간에 대한 학생 예약은 즉시 확정한다.
- 선생님 수락/거절 대기열은 만들지 않는다.
- 선생님이 취소해야 할 경우 사유를 남기고 QC·보충수업 정책과 연결한다.

### ADR-007 — 예약은 Alton이 원본이고 Calendar는 사본이다

- 예약 생성 시 DB에서 먼저 슬롯을 잠근다.
- 중복예약을 DB 제약과 트랜잭션으로 막는다.
- Google 이벤트 생성이 실패하면 예약을 실패/복구 가능한 상태로 남긴다.
- Google 이벤트 ID, Calendar ID, Meet URL, 마지막 동기화 시각을 DB에 저장한다.
- 예약·취소 API는 idempotency key를 사용한다.

### ADR-008 — 상담 정보 수집과 시간 선택을 한 흐름으로 만든다

- 랜딩에서 먼저 자체 인테이크 폼을 작성한다.
- 제출 성공 후 상담 가능 시간을 보여준다.
- 상담 일정은 `official@alton.education` 또는 별도 상담 전용 Calendar에 생성한다.
- 익명 방문자에게 Google 계정 로그인을 요구하지 않는다.

### ADR-009 — 계정은 체험 수업 전에 생성한다

고객 여정은 다음 순서다.

```text
상담 신청
→ 상담 예약/완료
→ 체험 선생님 선정
→ 학생·학부모 계정 초대
→ 무료 체험 세션 생성·예약·진행
→ 계약 의사 확인
→ 계약서 서명
→ 결제
→ 정식 등록 활성화
```

- 계약서 발송이 계정 생성의 트리거가 되어서는 안 된다.
- 체험 세션과 정규 세션을 구분하되 같은 세션뷰를 사용한다.
- 체험 수업의 기본 길이는 60분이다.
- 체험 수업은 학생의 정규 수업권을 차감하지 않는다.
- 체험 수업을 진행한 선생님에게는 회사가 비용을 지급한다. 선생님 입장에서 체험 수업은 유급 수업이다.
- 체험 수업 지급 단가는 해당 선생님의 기존 정규 수업 시급과 동일하다.
- 체험 수업 비용은 학생 계약·결제와 분리된 회사 부담 비용으로 기록한다.
- 체험 수업은 자녀당 1회 제공한다.
- 체험 수업 당일 취소 또는 노쇼에는 선생님 비용을 지급하지 않는다. `당일`은 수업을 담당하는 선생님의 IANA timezone상 수업 예정일을 기준으로 판단한다.
- 체험 완료는 계약 진행 자격을 만들 뿐 계약·결제·정식 등록을 자동 확정하지 않는다.
- 계약과 정식 등록은 자녀별로 각각 생성하고 관리한다.

### ADR-010 — Google Docs는 편집 가능한 iframe으로 구현하지 않는다

- 앱 안에는 문서 메타데이터와 읽기 전용 미리보기만 제공한다.
- `Google Docs에서 편집` 버튼으로 새 탭을 연다.
- 문서는 선생님·학생의 Google 이메일에만 편집 권한을 부여한다.
- `Publish to web`이나 `Anyone with the link`를 수업 문서에 사용하지 않는다.

### ADR-011 — Drive 전면 통일 대신 혼합 저장소를 사용한다

- 회사 문서, 계약서, Google Docs는 Shared Drive에 둔다.
- 세션 보충자료는 Supabase Storage에 둔다.
- DB에는 외부 URL만 저장하지 않고 provider, file ID, 소유·접근 범위를 함께 저장한다.

### ADR-012 — Google eSignature는 파일럿에서 수동 운영한다

- 자동 발송이나 웹훅 완료 감지를 구현하지 않는다.
- 관리자 포털에서 준비/발송/서명확인/완료 체크리스트를 제공한다.
- 실제 서명 문서는 Shared Drive에 저장하고 Drive file ID를 DB에 기록한다.
- 계약량이 증가하면 전용 전자서명 서비스를 재평가한다.

### ADR-013 — 선생님 매칭은 자녀·과목 단위로 관리한다

- 체험 수업을 진행한 선생님을 해당 자녀·과목의 정규 담당 선생님으로 기본 승계한다.
- 관리자는 자녀·과목별로 담당 선생님을 변경할 수 있다.
- 한 과목의 선생님을 변경해도 다른 과목의 매칭에는 영향을 주지 않는다.
- 매칭 변경 시 이전 선생님, 새 선생님, 대상 자녀·과목, 적용 시점, 변경 사유, 변경 담당자를 이력으로 남긴다.
- 완료된 과거 수업은 당시 담당 선생님과 정산 정보를 유지한다.
- 이미 확정된 미래 예약은 선생님 변경만으로 자동 이전하지 않는다. 관리자가 기존 예약을 취소·재예약하는 명시적 절차를 거친다.

## 6. 의도적으로 하지 않는 것

- Google Classroom 도입
- Gmail로 인앱 메시지 이전
- 세션뷰를 외부 LMS로 교체
- Google OAuth와 예약 시스템의 동시 전환
- 편집 가능한 Google Docs iframe 개발
- 모든 학생 파일에 Google Drive ACL을 생성
- 선생님 예약 수락/거절 워크플로우
- 신규 Zoom 녹화 요약 기능

## 7. 운영·보안 원칙

- Google service account key와 Supabase service-role key는 Vercel 환경변수에만 저장한다.
- Google domain-wide delegation은 Calendar/Drive에 필요한 최소 scope만 허용한다.
- Calendly webhook은 보완하지 않고 출시 전 코드와 배포 환경에서 제거한다.
- 관리자·선생님 계정 종료 시 Workspace 접근, 공유 문서, 활성 세션을 함께 회수한다.
- 모든 시각은 DB에 UTC로 저장하고 사용자·선생님의 IANA timezone을 별도로 저장한다.
- 외부 이벤트 생성·취소는 감사 로그를 남긴다.
- Google API 실패를 사용자에게 성공으로 표시하지 않는다.

## 8. 성장 후 재검토할 항목

- Google eSignature 수동 처리량이 월 20~30건을 넘을 때 전용 서비스 재도입
- 선생님 수가 증가해 Calendar 동기화 비용과 채널 관리가 커질 때 push notification 도입
- Google SSO와 Supabase identity linking
- 상담 담당자 다수 운영 시 round-robin 배정
- 학생 보충자료의 장기 보관 비용과 보존 정책
